- ~~`AGENTS.md` project identity is wrong in four places~~ — **resolved 2026-08-03.** Corrected against the ratified brief: Actions named as a non-goal with `gh` retained, the operator console added as a first-class surface, the two deliverables and their differing risk profiles stated, the contract named as what fixes a deployed instance's operations, the workflow-engine boundary recorded, and `blog-mcp` re-described as load-bearing prior art rather than a place to look.
- **Per-repository capability narrowing versus session-level tool discovery.** The build-time-versus-deploy-time conflict recorded here earlier was overstated and is now resolved: the contract enumerates which operations exist (fixed per image), declarations say which repositories exist (runtime data), and operations take a repository as a parameter rather than being compiled per repository. What remains is narrower. `MCP-NEXT.md` §9.4 omits a tool from `tools/list` when the session lacks its capabilities — a session-level decision. If declarations narrow capabilities per repository, discovery cannot express that, because one listing serves all repositories in the session. Per-repository restriction would therefore have to happen at dispatch only, which is weaker than the "capability filtering affects discovery and dispatch" rule the prior art states.
- **Deployment-time locking is per-deployment; `capabilities.ts` is per-consumer.** The prior art grants profiles to actors (UI, cron, watcher). The brief locks an instance at deploy time. Both granularities may be needed and their relationship is undesigned.
- **Every API endpoint and console view is repository-implicit.** `blog-mcp` binds one container to one repository, so `/api/repo/status`, `/api/log`, `/api/branches` and every view take no repository parameter. One-instance-many-repos gives every one of them a repository dimension, and the console needs a repository list or selector view with no precedent to copy. This is the bulk of the real work in deliverable 2 — not porting five views, but adding a dimension none of them have.
- **How many deployments are there? Explicitly undecided.** The model is base image providing generic git operations and the base console, with derived images adding workflows and their own views — `SubZeroDev.Blog` being the exemplar. Stated verbatim: "Not sure how to solve this yet." Either the operator runs one composed image carrying every layer, or a base deployment plus one container per derived consumer, each with its own console at its own URL. This bears on what "a common place" means, on what the console aggregates, and on whether "one instance, many repositories" survives contact with layering.
- **How consumer views reach the frontend bundle. Deferred to `/design`.** Extension happens at image build, but the console is a separate frontend project in the prior art and a bundle must be built to gain routes. Options raised: the derived image rebuilds the bundle from base sources; the base publishes a versioned package the consumer's build consumes; or a prebuilt bundle discovers views at runtime, which would place UI outside the fingerprinted contract and defeat the reason image-build extension was chosen.
- **Naming the six makes the escape-hatch conflict concrete.** The definition of done now blocks `reset --hard`, `clean`, `push --force`, `rebase`, `branch -D` and history rewriting on the default path, while the escape hatch reaches any git operation — which is exactly those six. The gate and the hatch are now demonstrably about the same set, rather than vaguely in tension.
- **Credential isolation: convention or enforced boundary? Deferred by decision.** The brief said "a workflow acting on one repository can never reach another's". One process holding every credential can deliver *not given to*, not *cannot be reached*. Options raised: scoped lookup within one process; an enforced boundary via separate processes or users; an external store fetched per operation; or weakening the claim to what is actually true. Deliberately left for later — the brief's wording has been softened meanwhile so it does not assert something undelivered.
- **The escape hatch negates the prior art's central safety property.** The decision "full git behind an escape hatch" was taken before the prior art had been read. README's "What is deliberately not a tool" states that the tool surface *is* the safety boundary — no `reset --hard`, `clean`, `push --force`, `rebase`, `branch -D`, no history rewriting, by construction. Reinforced six ways: no force option in `blog_push`'s schema; no `blog_merge_pr`; no rebase tool "by design never will be"; `/api` an explicit route table rather than a call-any-tool proxy; `TODO-NEXT.md` §14 forbidding one; and capability tiers gating registration rather than behaviour. The registration argument names the threat directly: "a tool that doesn't exist in the list a client sees cannot be talked into existing by text embedded in a blog draft or a PR comment." Since the primary consumers here are agent runtimes reading repository content and PR comments, a registered full-git hatch is reachable by prompt injection, and its audit log records an escalation rather than preventing one. A narrower alternative exists in the prior art: `blog_restore_paths` meets the discard need with an explicit allowlisted path list, only back to `origin/<base>`, refusing staged paths and unable to delete untracked files. **Not reconciled — the decision stands and this is recorded against it.**
- **A connected MCP client can hold a stale tool catalogue.** A client that ran `tools/list` before a redeploy and never re-ran `initialize` keeps the old catalogue, and the prior art records that there is no supported way to push a refresh (`blog-mcp` issue #108). "A deployed instance executes only its predefined operations" is therefore true of the server and not of every client's view of it.
- **Repository config must stay descriptive.** Settled for now (see the decision below), and it holds only while the format carries no permission-shaped field. Worth a check at `/contract` rather than trusting anyone to remember.
- **Renaming ~30 tools is a breaking change with a policy attached.** `MCP-NEXT.md` §7.5 makes tool names public API identifiers and requires a documented deprecation period or an explicit major version change to rename one. Generic tools should lose the `blog_` prefix, but `SubZeroDev.Blog` is a live consumer. Compatibility shim, deprecation window, or clean break — undecided.
- **Naming is unsettled.** `SubZeroDev.Git` is the repository name and the working default. `Gittify` was raised and collides with `Gitify`, the GitHub-notifications app. `GitFlows` was raised and rejected for colliding with Driessen's git-flow branching model. The service, image and MCP server names are separate from the repository name and none are decided.
- **The per-process mutex is the only concurrency guarantee.** `blog-mcp`'s README warns that two containers against one working tree race, because the lock serialises within a process only. One instance holding many repositories makes the process boundary the sole thing preserving the serial guarantee, and nothing yet prevents a second instance being started against the same storage.
- **Deployment-time workflow locking and the escape hatch have not been reconciled.** A deployed instance executes only its predefined workflows, yet the operation surface says full git is reachable via a deliberate hatch. Either the hatch is one of the capabilities granted or withheld per deployment, or it sits outside the lock and the restriction covers only the default path. The two readings differ in what the safety guarantee can claim. Flagged in `00-brief.md`; `/design` must settle it.

### 2026-08-03 — `.gitattributes` pins LF; `core.autocrlf` overridden per repository
Context: Every commit warned "LF will be replaced by CRLF the next time Git touches it". `core.autocrlf` is `true` on the primary Windows host, so checkouts would carry CRLF while the house convention in `AGENTS.md` is LF. This project ships a container with an entrypoint script, and a shell script checked out with CRLF fails inside a Linux container with a bad-interpreter error naming neither the script nor the line endings.
Chosen: `* text=auto eol=lf` in `.gitattributes`, plus explicit `binary` for raster and archive types. One file, effective on every host and every clone regardless of local git configuration.
Rejected: **Force LF for scripts only** — narrower, and it leaves two rules to remember whenever a new file type appears. **Defer until the first script exists** — which is exactly when someone is already debugging a container that will not start. **Set `core.autocrlf=input` globally on the host** — fixes every repository at once and silently changes behaviour for the other twelve in the estate.
Reversibility: cheap, though a later change would rewrite the working tree of every clone.

### 2026-08-03 — Tool renaming is a clean break at cutover, no aliases
Context: Roughly 30 repository-generic tools carry a `blog_` prefix. `MCP-NEXT.md` §7.5 makes tool names public API identifiers and requires a documented deprecation period or an explicit major version change to rename one. `SubZeroDev.Blog` is a live consumer of every one of them.
Chosen: Operation-descriptive names from first release, with `SubZeroDev.Blog` migrating in the same coordinated cutover. No aliases, no deprecation window. Gated as definition-of-done item 21: no tool ships under a name intended for removal.
Rejected: **Aliases for a stated window, then removed** — follows §7.5 literally and lets the two repositories move independently; rejected because every alias is a removable name sitting in `tools/list` for an agent to pick, and doubling the tool list during the window works against the registration-is-the-boundary principle. **Aliases kept permanently** — nothing ever breaks, and the generic surface carries `blog_` names forever, which is the coupling this extraction exists to remove. **Defer to `/contract`** — naming is a contract concern, but the policy determines how the Blog cutover is sequenced and was needed sooner.
Reversibility: expensive after release — a shipped name is a published identifier.
Note: §7.5's protection exists for consumers an author does not control. Here both repositories and the sole operator are the same person, so a deprecation window buys nothing that a coordinated change does not.

### 2026-08-03 — The mutex covers mutations only, not reads or waits
Context: The brief said "one operation at a time, globally across all repositories". `blog-mcp` serialises repo-mutating calls only — `blog_diff` and every read tier run outside the mutex — and every `wait_*` tool caps at 1800 seconds. Under the literal reading a single CI wait would hold every repository for up to half an hour.
Chosen: Repo-mutating operations serialise globally. Reads and monitoring waits run outside the lock.
Rejected: **Everything including waits** — simplest failure model, and unusable past one repository. **Waits yield between polls** — keeps long monitors from blocking at the cost of a wait observing state changing underneath it. **Per-repository mutation locks** — would reverse the global-serialisation decision and make the failure model several half-done operations rather than one.
Reversibility: cheap.

### 2026-08-03 — Any host for local git; pull-request tooling is GitHub-only
Context: "Any git repository, unbounded" sat against a generic tool set of which roughly a third is GitHub-shaped — `create_pr`, `auto_merge`, `pr_status`, `check_status`, `deploy_status`, `verify_published_url` — plus `required_checks` and `deploy_workflow` in the declaration format.
Chosen: Local git works against any host. Pull requests, checks, merges and deploy monitoring are GitHub-only and unavailable elsewhere. A declaration states its host and gets the tool set that host supports.
Rejected: **GitHub-only, "unbounded" meaning count alone** — smallest and most honest, rejected as too narrow. **A host abstraction proven against a second implementation** — the only reading that makes "no assumptions about host" fully true, and materially the largest. **GitHub-only now with a seam kept for later** — costs design discipline and no second implementation; retained as a live option for `/design`.
Reversibility: moderate — adding a host later is additive if the seam exists, invasive if it does not.
Open: A per-declaration tool set varies by host, while the contract fixes the tool list per image and `tools/list` is decided per session. This is the same shape as the per-repository capability-narrowing question already logged, and the two should be resolved together.

### 2026-08-03 — Each managed repository carries its own endpoint configuration
Context: Generalises `blog-mcp`'s `.config/blog.json`, which already carries `clone_url`, `base_branch`, `required_checks`, `deploy_workflow` and `branch_prefixes` inside the target repository. Stated verbatim: "This will be built in such a way that the local repo will specify the config for it's endpoints."
Chosen: The managed repository declares the configuration for its own endpoints.
Rejected: **Configuration held entirely operator-side** — removes the escalation-by-commit risk outright, and forces every repository-specific detail through deployment configuration, which does not scale to unbounded targets and contradicts "onboarded by declaration alone".
Reversibility: expensive — it sets where the declaration format lives and therefore who can change it.

### 2026-08-03 — Repository config is descriptive; no permission-ceiling mechanism
Context: A concern was raised that repository-controlled config confers authority by commit — an actor able to write the file widens its own permissions. Two guards were proposed: a two-layer split allowing repository config to narrow but never widen beneath an operator ceiling, and reading config from `origin/<base>` rather than the working tree. Both were declined: "No, none of that is needed, not today" and "Irrelevant now."
Chosen: Repository config is descriptive only — base branch, required checks, deploy workflow, branch prefixes, as `.config/blog.json` already is. Authority stays operator-side in deployment configuration and capability profiles, matching how `blog-mcp` already separates repository facts from `BLOG_MCP_ALLOW_REMOTE` and `BLOG_MCP_READ_ONLY`. No ceiling mechanism, no authoritative-ref rule.
Rejected: **Two-layer split with narrowing only** — would make repo config safe to treat as untrusted, at the cost of machinery not needed while config carries no permissions. **Config read from `origin/<base>`** — would stop a feature branch changing the rules governing it, same cost, same reason. Both retained here as known and available, not lost.
Reversibility: cheap to add later — both guards sit outside the config format rather than inside it.
Reopen when: any permission-shaped field is added to repository config — anything a caller could set that widens what the service will do. At that point commit access becomes authority and both guards return. The concern was never about the config format; it was about whether the format carries permissions. It does not.
Known and retained: `blog-mcp`'s `loadConfig(repoRoot)` reads `.config/blog.json` from the working tree, so the file can differ per branch. With descriptive config the practical reach of this is limited to repository facts — though `required_checks` is one of them, so a branch can still alter which checks its own workflow waits for. Reported for the record; no action taken.

### 2026-08-03 — Workflow sequencing moves server-side as transactional composites
Context: The publishing sequence currently runs in the browser — `ComposeView` calls `/api/branch`, `/api/posts`, `/api/stage`, `/api/commit`, `/api/push`, `/api/pr` in order. `TODO-NEXT.md` §7.1 records the resulting incident (a commit stranded on `main` when branch creation re-based from `origin/main`) and §7.3 prescribes replacing client orchestration with one transactional preparation tool.
Chosen: The base exposes transactional composites that perform several git steps atomically, `prepare_publish_branch` being the worked example. A caller invokes one operation rather than sequencing six.
Rejected: **Primitives only, consumer orchestrates** — consistent with "workflows stay domain code" and carries forward exactly the pattern that stranded the commit. **Both, composites over primitives** — composites for known-dangerous sequences and primitives elsewhere; rejected as two ways to do the same thing with different safety properties. **Composites only, primitives behind the escape hatch** — the strongest safety reading; retained as a live option for `/design` since it follows naturally from the hatch decision.
Reversibility: expensive — it decides the shape of the public operation surface.
Note: This does not reopen the workflow-engine non-goal. A transactional composite is handwritten domain code with a fixed reviewed sequence — no declarative definition, no conditionals, not authored by a caller. The non-goal forbids the engine, not the composites.
Consequence: The safety gate becomes enforceable rather than advisory. A client cannot skip a step it never orchestrates.

### 2026-08-03 — Consumers extend by building a downstream image from the base
Context: An extensible console appeared to conflict with `MCP-NEXT.md`'s build-time contract fingerprint, which is verified at startup and fatal on mismatch — consumer views arriving later would sit outside the contract. Stated verbatim: "i can user docker to build from base."
Chosen: The base ships as a container image. A consumer builds its own image `FROM` that base, adding its views and its domain tools. Its contract is compiled and fingerprinted during *its* build, with the consumer's additions already present. Extension happens at image build time, never at runtime.
Rejected: **Runtime plugin registration** — would place consumer views and tools outside the fingerprinted contract, making the immutability guarantee cover only part of the running system. **Consumer forks the base console** — no shared seam to maintain, and every base improvement becomes a merge.
Reversibility: cheap — it follows the container model the prior art already uses.
Consequence: The apparent conflict was not real, and the contract-versus-declaration tension recorded in `## Open` was overstated. The contract enumerates which operations exist and is fixed per image; declarations enumerate which repositories exist and are runtime data; operations take a repository as a parameter. The two are orthogonal, and "onboard a repository by declaration alone, no rebuild" survives.
Open: If each consumer is its own image and container, the deployment topology is no longer obviously "one instance". See `## Open`.

### 2026-08-03 — Not a general workflow engine; flows deferred to a later layer
Context: `MCP-NEXT.md` §3 states as a non-goal that it "will not become a general workflow engine. Multi-step publishing remains Blog-Bot domain behavior rather than a generic contract feature." The brief's problem statement asks to "lock deployments to pre defined worflows", which read as crossing exactly that line. ### 2026-08-03 — One operator identity; local credentials plus pluggable auth providers
Context: Authentication moved three times across the interview — multi-user auth chosen, then dropped for single operator, then restated as "user/password, or user/2fa, and oauth too", then extended to "user/password here, and generic auth providers". Reading `blog-mcp/src/serve/oauth.ts` showed its OAuth is an authorization server for MCP clients whose login delegates to the single-operator password, so it never conflicted with single-operator at all.
Chosen: One operator identity with a username. Provable two ways, both required: local username and password with 2FA available, and federation to a generic, vendor-pluggable external identity provider. Separately the service remains an OAuth authorization server for MCP clients. No accounts table, no roles.
Rejected: **Real accounts without roles** — several logins, all equal; contradicts the multi-tenancy non-goal. **Accounts with roles** — per-user reach over repos, workflows and the escape hatch; coherent with one-instance-many-repos and a substantially larger project that reopens concurrency. **Keep `blog-mcp`'s bare password** — nothing new to build, and no route to federation.
Reversibility: cheap for the local half, expensive for the provider half — a pluggable provider abstraction is hard to retrofit onto a hardcoded one.
Note: The two OAuth roles are distinct and must not be conflated. As authorization server the service authenticates MCP *clients*; as relying party it authenticates the *operator*. Only the first exists in the prior art.
Open: Federation and single-operator are in mild tension. An external identity provider will happily assert many identities, so something must reduce that to one authorized subject — an allowlist, a claim match, or similar. Recorded rather than re-asked; single operator has been stated four times and is not in doubt.

### 2026-08-03 — Credentials are per-declaration and isolated
Context: A consequence of one-instance-many-repos that no interview answer had reached. `blog-mcp` needed exactly one credential and took it from the environment; per-repo containers gave credential isolation for free. A single instance removes that property silently.
Chosen: Each repository declaration names its own credential. A workflow acting on one repository cannot reach another's.
Rejected: **One shared credential across every declared repository** — simplest and closest to the prior art, but any workflow on any repo could push anywhere that token reaches, which is precisely the blast radius the single-instance topology creates. **Per-declaration via an external secret store** — strongest, keeps secrets out of both the declaration and the container environment; rejected for now as a dependency and deployment prerequisite, and retained as a live option for `/design`. **Defer to `/design`** — would have left the sharpest security question in the project unanswered going in.
Reversibility: expensive — it constrains the declaration format and the storage layout.

### 2026-08-03 — One instance serves many repositories; `blog-mcp`'s one-repo-per-container model dropped
Context: `blog-mcp` binds one container to one repository — a single `BLOG_MCP_CLONE_URL`, a single `/workspace/repo`. The brief asks for "a common place" for all repositories, which that topology cannot provide without an aggregator above it. The two readings were logged as open and then resolved directly.
Chosen: One instance serving many declared repositories. Per-repo declarations, per-repo capability profiles, per-repo credentials in one process, and a console that aggregates across repositories.
Rejected: **One instance per repository** — follows the proven model exactly, makes deploy-time locking trivially coherent (the instance *is* the repo binding), and keeps serial operation true by construction; rejected because "a common place" then means only a consistent way to deploy, not one surface. **One instance per repository now, aggregating console later** — defers the hard problem without designing it out. **Many repos with per-repo locks and parallel operation** — the most capable reading; rejected in favour of global serialisation, see below.
Reversibility: expensive — credential scoping, storage layout, the declaration format and the console's information architecture all follow from it.

### 2026-08-03 — Globally serialised by an in-process lock; "no locking" retracted
Context: An earlier interview answer made "no queue, no locking, no contention handling" a binding non-goal. Reading `blog-mcp/src/exec/repoLock.ts` contradicted it: that lock exists because the UI, external MCP clients and the scheduler share one working tree and one HEAD, and without it concurrent branch switches corrupt HEAD and `git add` hits `index.lock`. This project has the same three surfaces, and now serves many repositories from one process.
Chosen: One operation at a time, globally across all repositories, enforced by an in-process lock. `blog-mcp`'s promise-chain queue is the precedent. The non-goal narrows to distributed and multi-node concurrency.
Rejected: **Genuinely no lock** — the reference's own comments record that this corrupts HEAD in practice. **Reject the second caller rather than queue** — arguably better for agent callers, which handle an explicit error better than a long blocking wait; retained as a live option for `/design`. **Per-repo locks with parallel operation across repositories** — the natural fit for one-instance-many-repos and the most capable; rejected to keep the failure model at exactly one half-done operation.
Reversibility: cheap to tighten, expensive to loosen — the serial assumption will spread through the workflow layer.
Note: The retracted non-goal was a category error worth naming. One-operation-at-a-time is the *outcome a lock produces*, not the absence of one.

Rejected: **Both out, call GitHub's REST/GraphQL API directly** — one less binary in the image and better aligned with "any git repository, unbounded" since `gh` is GitHub-only; retained as a live option for `/design`, since the unbounded-targets decision will force the question anyway. **Both out, pure git with no host API** — would gut the definition-of-done item requiring an agent to complete a change through a merged PR. **Drop the non-goal entirely** — loses a constraint that was genuinely meant.
Reversibility: cheap — `gh` is already isolated behind one module in the prior art.

### 2026-08-03 — Target repositories cloned on demand, not mounted from the host
Context: With Actions out, the container needs its own route to target repositories. `SubZeroDev.Blog`'s server works against a local working copy, so inheriting that was the obvious default.
Chosen: The container clones from the remote when a declaration is exercised, and manages its own storage lifecycle. Nothing pre-existing on the host is assumed.
Rejected: **Mount local clones from the host** — how the Blog server works today, but it ties the container to one machine's directory layout and contradicts "any git repository, unbounded". **Remote git protocol only, no working copies** — constrains which operations are expressible at all, for a saving the brief never asked for.
Reversibility: expensive — storage lifecycle, disk pressure, and clone caching all follow from it.

### 2026-08-03 — Single operator; multi-user auth rejected after being chosen
Context: Multi-user authentication was selected during the interview, then withdrawn when its cost was made explicit: real accounts mean two callers can act at once, which is exactly the contention the serial answer had already excluded. Both could not stand in a binding brief.
Chosen: Single operator. No accounts, roles, sessions, or per-user permissions. One caller, one repository at a time — no queue, no locking. Both are non-goals.
Rejected: **Many users, globally serialised operations** — the coherent reconciliation and the recommended option; makes auth meaningful while preserving the single-operation failure model, at the cost of building concurrency control. **Multi-user with real concurrency** — per-repo locking and conflict detection; a substantially larger project. **Accounts as login only, second caller rejected** — keeps the serial guarantee but pays for an auth system that buys nothing beyond a shared secret.
Reversibility: cheap to add auth later; expensive to add concurrency later, because the serial assumption will have spread through the workflow by then.

### 2026-08-03 — Full git behind an escape hatch, workflow as the default path
Context: `AGENTS.md` frames the product as git operations "behind a pre-defined workflow", which reads as workflow-only. The interview declined that non-goal and asked for full git with the workflow as default.
Chosen: The pre-defined workflow is the default path. Lower-level git is reachable by deliberately taking an escape hatch. The workflow path rejects unsafe operations; the hatch may reach anything, and every use is logged and attributable.
Rejected: **Workflow only** — the strongest safety story, and what `AGENTS.md` implies; rejected as too confining in practice. **A hard floor no surface can cross** — a named set (force-push, history rewrite) unreachable even via the hatch; the most falsifiable guarantee, not taken. **Hatch restricted to the console, never MCP** — would have made the guarantee absolute for agent callers specifically.
Reversibility: expensive — it decides what the safety gate can honestly claim, and the definition of done is written against it.
Consequence: "Unsafe operations provably blocked" now asserts something narrower than it appears to. It tests the default path only and makes no claim about the hatch. Stated as such in the brief so the gate stays falsifiable.

### 2026-08-03 — Any git repository, unbounded
Context: The alternatives ranged from proving it against two repositories to accepting any repository at all. The estate is twelve repositories, which would have been a defensible bound.
Chosen: Unbounded. No assumptions about structure, host, or conventions; the declaration format must not encode `SubZeroDev.*` habits.
Rejected: **The ~12 `SubZeroDev.*` repositories** — a knowable, enumerable set that would let the declaration format lean on shared conventions. **Start with one or two** — lets the format tighten around real cases before generalising, and is the cheaper path to a working system.
