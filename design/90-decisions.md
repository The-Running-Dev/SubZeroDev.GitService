### 2026-08-03 — The audit log is hash-chained: tamper-evident, not tamper-proof
Context: Open question 5, raised when triaging the first redteam pass. Item 8 wants hatch use attributable, and `git.raw` is the one surface that can rewrite the log recording it. The answer had to land before `/contract`, because it fixes the audit line format and retrofitting a chain over a written trail is a migration.
Chosen: A per-line hash chain — sequence number, previous line's hash, own hash over the canonical serialisation plus that previous hash — spanning rotated segments, with the chain head mirrored into the structured store and verified end to end at boot. A broken chain is reported and never fatal, because refusing to start on a corrupt trail would hand anyone able to corrupt it a denial of service. The claim is precise: truncation and edited lines are detectable; a service-privileged rewrite of both the log and the mirrored head is not, so this is detection rather than prevention.
Rejected: **An external append-only sink** — genuinely tamper-proof rather than tamper-evident, and it survives volume loss too; deferred because it adds a deployment dependency the brief never scoped and makes an unwatched instance depend on a second service being reachable. Worth revisiting if such a target ever exists. **Accept refusal-time attributability as the whole claim** — free and honest, and it leaves item 8 claiming materially less than it appears to for the one surface that can rewrite its own evidence. **Refuse to start on a broken chain** — the strongest reading of an audit guarantee, and a self-inflicted outage trigger.
Reversibility: cheap now, expensive once lines exist — which is exactly why it was answered before `/contract`.

### 2026-08-03 — Volume provisioned generously; eviction is exceptional and notifies
Context: Open question 6. The eviction machinery, the watermark values and the four retention windows all depended on a number only the operator has.
Chosen: A volume of the order of 100 GB for roughly a dozen declarations — several times the working set. Watermarks at 85 % (request a maintenance pass, retention first, eviction only if that was not enough) and 95 % (refuse operations needing space). Eviction fires the notifier, because at this sizing a released clone means the estate is outgrowing its disk rather than that housekeeping ran. Retention defaults: audit 90 days at 64 MB segments, settled journal 30 days, delivered outbox 14 days, three pre-migration backups. All four are configuration.
Rejected: **Tight volume with routine eviction** — right for a small or shared volume, and it makes unpinned clones re-clone often, paying network time on first use and making eviction ordinary enough that its notification would become noise. **A volume so large eviction never fires** — simplest operationally, and it leaves the eviction path untested until the day it finally runs, which by then is the worst day to discover it.
Reversibility: cheap — every value is configuration, and the interlock's behaviour does not change with the thresholds.

### 2026-08-03 — The lock protocol is four rules, not one ordering
Context: The design's deadlock argument rested entirely on "materialisation before mutation, never the reverse". Review found the design's own disk-pressure path violating it: the watermark check fires after each mutation, eviction is covered by the materialisation mutex, so the post-mutation check acquires materialisation after mutation. Bounded waits would have degraded the resulting cycle into spurious `conflict`s rather than a hang, which is worse — the failure would have looked like contention, at disk pressure, in production.
Chosen: Four rules. The order stands; a caller holds the materialisation lock for the whole operation and releases in reverse; eviction never runs while the global mutation lock is held, so the watermark check requests a maintenance pass instead of evicting inline; and eviction refuses while a per-declaration active-operation count is non-zero. The counter is a non-blocking pin, not a third lock.
Rejected: **Order alone** — what the document said, and it is unsound. **Release the materialisation lock after the ensure step** — the intuitive scope for it, and it opens a window where eviction removes a clone between the ensure and the journal write, producing an intent record with an unre-derivable pre-state. **Make reads take the materialisation lock** — closes the read-versus-eviction race correctly and reintroduces exactly the blocking the read exemption exists to remove.
Reversibility: expensive — the clone store, dispatch, journal recovery and the eviction interlock are all written against it.

### 2026-08-03 — An unmaterialised declaration is servable; the concurrency argument was wrong, not the control flow
Context: Two statements could not both be implemented. The concurrency section justified concurrent clone-of-A-with-mutation-of-B by asserting no session can name a declaration until its clone is `ready`; the control flow made a session's `tools/call` the thing that triggers the clone.
Chosen: The control flow reading, because definition-of-done item 5 forces it — clone-on-demand means the call is the trigger, and the other reading leaves headless onboarding with no trigger at all. The safety argument is redone on the real property: a clone takes only that declaration's materialisation lock and never the global mutation lock. Discovery against a treeless declaration is now analysed rather than assumed away, and three states are distinguished — no clone, materialising, and `recovery-pending`.
Rejected: **Keep the unservable reading and add an explicit materialise operation** — restores the original safety argument verbatim, and it fails item 5's "a running instance picks it up and clones it" by requiring an operator step the item exists to remove.
Reversibility: cheap now, expensive once session establishment, discovery filtering and the clone store each encode an answer independently.

### 2026-08-03 — Grants, tokens and revocation are modelled; a grant epoch makes a frozen session narrowable
Context: Durable grants are definition-of-done item 12's headline departure and item 20 requires revocation documentation, yet OAuth clients, grants and tokens appeared once as a phrase in a storage-kinds row and were never modelled. No revocation existed anywhere — no capability, route, view or entity. Combined with a session grant frozen for the session's lifetime, the operator's only revocation mechanism during an incident was restarting the container.
Chosen: Three entities with `revokedAt` timestamps rather than deletes, cascade evaluated at check time, plus a `grantEpoch` per declaration that dispatch compares against the epoch a session froze at. A moved epoch forces a recomputation that can only narrow, so both properties hold at once: nothing at runtime widens a live session, and a revocation lands on the very next call. Revocation is console-only under a new `auth.manage`.
Rejected: **Recompute the grant on every call** — simplest, and it discards the prior art's fixed-at-`initialize` rule, letting a widened declaration grant reach a live session. **Keep the freeze and accept revocation-at-session-end** — what the document said, and it is a hole exactly where it matters operationally. **Delete revoked rows** — smaller store, and a store that forgets what was revoked cannot answer the question the revocation was raised to answer.
Reversibility: expensive — revocation cuts across authorization, session lifecycle, the store schema, the console and the contract.

### 2026-08-03 — The global mutation mutex stays; the throughput ceiling is stated instead
Context: Fetch and push take the global mutex, and the lock table claimed a hold time of "milliseconds to seconds" — false for a network transfer, and unenforced, since only the clone had a cap. At a hundred declarations a one-line commit can queue behind a transfer on an unrelated repository.
Chosen: Keep global serialisation. Correct the table, give fetch and push their own 300 s caps, and record the ceiling as an honest limit naming the condition to revisit it.
Rejected: **Per-declaration mutation locks** — raises throughput and breaks the invariant every other part of the design is written against, that a crash leaves exactly one half-done operation, which is what makes recovery classification tractable. Revisit only with that invariant reopened. **Leave the column as written** — an unenforced assertion that reads as a guarantee.
Reversibility: expensive to change later, which is why the revisit condition is named rather than left implicit.

### 2026-08-03 — Boot starts transports before recovering; recovery is per-declaration and lazy
Context: The boot path re-derived every clone's state and ran the recovery pass for every declaration before transports started, both involving git subprocesses per clone. At a few hundred clones a restart means minutes of total unavailability, to recover state concerning at most one declaration — so the thing the journal makes safe becomes the thing the operator avoids.
Chosen: Readiness and transports first. A declaration with unsettled entries is `recovery-pending`, serves reads, refuses mutations, and recovers on first use or a background sweep. Boot also gained a pending-scheduled-job re-validation sweep, so an image upgrade that renames a tool or changes a schema surfaces next to the fingerprint checks that caused it rather than weeks later at fire time.
Rejected: **Eager recovery before readiness** — the stronger guarantee, kept where it is load-bearing (no mutation on an unrecovered declaration) and dropped where it was only tidy.
Reversibility: expensive — servability, readiness semantics and the `needs-attention` blocking model move together.

### 2026-08-03 — `RepositoryConfig` is read from `origin/<base>`, and the config path is not writable by default
Context: The design never said which ref the repository-supplied config is read from. The working tree of a long-lived clone is wherever the last operation parked it, including a branch the calling agent just created, so a working-tree read lets a caller author the configuration governing its own call. `requiredChecks` grants no capability but defines what "green" means to the unwatched flow of item 13.
Chosen: Read from `origin/<base>`, as the prior art does for `blog_log` and for the same reason. Exclude the config path from `writablePathPrefixes` by default. Invalidate the cache on fetch and on any movement of `origin/<base>`.
Rejected: **Read from the working tree** — matches what an operator sees when they look at the clone, and it makes a descriptive format load-bearing for a safety gate. **Leave the ref unstated** — every consumer would have baked in the working-tree read before anyone noticed.
Reversibility: cheap now; expensive once composites, monitors and reporting each read config their own way.

### 2026-08-03 — Nine contained gaps closed together
Context: The same review found nine defects that were each a missing paragraph rather than a missing design: no exit from `attention`, lockout recovery present only as the word "break-glass", notifications dropped silently, reads racing eviction, `declaration.manage` described as a configurable default when the session model forbids it structurally, no retention policy for four append-only stores, no console CSRF or session lifecycle, a credential-failing mark with no clearing rule, and scheduled-job validation described as creation-only.
Chosen: Close all nine in one pass — `attention.resolve` and `auth.manage` capabilities with the three operator views that exercise them; recovery codes plus break-glass, stated as independent of each other and of the identity provider; failed outbox rows surfaced rather than dropped, and a notify-on-recovery rule; eviction gated on the active-operation count; structural rather than configurable phrasing for the operator-only capabilities; a retention table covering audit, journal, outbox and pre-migration backups; cookie, CSRF, timeout and logout rules in L5; a credential mark that clears on observed rotation or by hand; and fire-time plus boot-time job re-validation.
Rejected: **Defer them to `/contract` or `/slices`** — each is small enough to look deferrable, and together they are the difference between a design that survives its first incident and one that discovers its gaps during it.
Reversibility: cheap individually; the retention and revocation halves become migrations once data exists.

### 2026-08-03 — `git.raw` writes two audit lines
Context: The audit entry carries result kind and changed paths — post-execution facts — while the hatch was specified to refuse to run if its line could not be written, and the boundary table claimed no state left behind. One line cannot both precede execution and contain its result. An earlier edit the same day narrowed the durability claim but left this sequencing untouched.
Chosen: An intent line carrying the argument vector before the child process starts, and an outcome line carrying the result afterwards, correlated by `operationId`. Only the intent append can abort the call. A failed outcome append is a gap in the trail, not an unlogged execution, and the boundary table now says so.
Rejected: **One line written after execution** — keeps the entry shape, and forfeits the only property item 8 claims for the hatch. **One line written before, without the result** — preserves the refusal guarantee and makes the hatch the one operation whose outcome the audit trail never records.
Reversibility: cheap — a sequencing decision in one module.

### 2026-08-03 — `git.raw` redteam finding triaged: audit integrity is the defect, the rest is already claimed
Context: A `/redteam` pass by Codex filed one BLOCKING finding — that `git.raw` collapses the repository and authority boundaries, because command execution reached through git's extension points can touch a sibling clone, the structured store, the audit log, or another declaration's credential resolver, and pinning the working directory does not confine a child process. The execution premise is correct and the design already concedes it. What had to be settled was which of the named consequences the documents actually claim to prevent.
Chosen: STRUCTURAL, scoped to audit integrity. One consequence is a genuine defect: the boundary table claimed durable attributability for the hatch while the same hatch can rewrite the JSONL afterwards, which is a document contradicting itself rather than a risk the brief accepted. The claim is narrowed to refusal at call time, the reachable surface is now stated explicitly in `10-design.md` § The escape hatch's residual risk, and tamper-evidence becomes open question 5 — it wants answering before `/contract`, because the answer fixes the audit line format.
Rejected: **BLOCKING as filed** — would carry a blocking finding into `/contract`; rejected because the blast radius claimed rests on two boundaries the documents never asserted. **Per-declaration credential isolation as a violated boundary** — the brief defers this explicitly and claims only that a credential is not *given* to an operation outside its declaration, not that it cannot be reached, so reaching one via the hatch is inside what is claimed. **The no-cross-repository non-goal as a containment guarantee** — it is a scope statement about operations never being treated as one unit, not a security boundary. **Reopening the hard floor** — considered and declined in the ratified brief; a redteam finding does not reopen a brief decision. **Recording the triage without changing the design text** — leaves "pinned working directory" reading as more confinement than it delivers.
Reversibility: cheap for the wording; the tamper-evidence answer behind open question 5 is expensive once the audit format is written.

### 2026-08-03 — Capability authority is a four-layer lattice that only narrows
Context: The brief flagged build-time-versus-deploy-time locking as something `/design` must settle: `MCP-NEXT.md` fixes the contract at build time and fingerprints it, while the brief describes the lock as fixed at deploy time, per instance. A separate open item recorded that the prior art's per-consumer profiles and the brief's per-deployment lock are different granularities with an undesigned relationship.
Chosen: Four layers, each a subset of the one above — contract set (image build, fingerprinted), deployment ceiling (deploy configuration), declaration grant (runtime data, per repository), session grant (actor profile intersected with OAuth scopes). The effective set for any call is the intersection. No operation anywhere adds a capability to a set. Both timings are true because build time sets a maximum and every later layer only narrows.
Rejected: **Compile the contract per deployment** — makes the lock literally what the brief describes, and breaks the fingerprint, since a contract baked at build cannot enumerate repositories declared later. **Let deploy-time configuration widen what the image ships** — the obvious way to make one image serve differently-privileged deployments, and it destroys default-deny, because the running tool set would stop being a subset of the reviewed one. **Two unrelated mechanisms, one per-deployment and one per-consumer** — closest to the prior art, and it leaves the per-repository dimension with nowhere to live.
Reversibility: expensive — every enforcement point, the declaration format and the contract's capability field all sit on it.

### 2026-08-03 — MCP sessions are repository-scoped; the resource indicator is the repository
Context: `MCP-NEXT.md` §9.4 omits a tool from `tools/list` when the session lacks its capabilities, and §13 requires capability filtering to affect discovery and dispatch. With one instance serving many repositories and one listing per session, a per-repository grant could only be enforced at dispatch — weaker than the rule, and it forfeits the registration-is-the-boundary property that carries the prompt-injection threat model.
Chosen: An MCP session binds to exactly one declaration at `initialize`. The canonical MCP URI is `/mcp/{declarationId}`, so the OAuth resource indicator *is* the repository. Discovery and dispatch both filter on the full intersection. The operator console session is unscoped and spans every declaration, because it has to aggregate. The repository stays a required field in every tool's input schema on every surface.
Rejected: **Repository-agnostic sessions, repository as a parameter only** — simpler and identical to the HTTP surface; rejected because per-repository narrowing then reaches dispatch only. **An optional repository field defaulted from the session binding** — better agent ergonomics, and the input schema would mean different things on different surfaces. A scoped session that passes the wrong repository gets `authorization` instead.
Reversibility: expensive — it sets the MCP URI shape, the OAuth resource identifiers, and therefore every issued grant.
Consequence: This also settles the logged tension about per-declaration tool sets varying by host. A `generic` declaration's grant cannot contain `host.*` capabilities, so the host-specific tools are filtered out of that session's listing. The contract still fixes one tool list per image.

### 2026-08-03 — One composed image, one deployment
Context: The brief left deployment topology explicitly open, bearing on what "a common place" means and on what the console aggregates. The layered-image decision (base plus derived) reads naturally as one container per consumer.
Chosen: One composed image carrying every layer the operator wants, deployed once. One login, one console, one storage volume, one instance lock. Consumer tools and views ship in the image for every repository and are withheld per declaration by the capability lattice.
Rejected: **A base deployment plus one container per derived consumer** — cleaner separation of consumer code, and it produces two consoles, two logins and two URLs, which is the "no common place" problem the project exists to solve; it also fragments one-instance-many-repositories into one instance per consumer. **A base deployment plus an aggregating console above it** — preserves separation and keeps one surface, at the cost of building an aggregation layer whose only job is to undo the split.
Reversibility: expensive — the storage lock, the console's information architecture and the session model all assume a single owner.
Consequence: The blog consumer's ~16 authoring tools and its two views are present in the image for repositories they make no sense for. That cost is paid by the lattice rather than by a second mechanism, which is the reason the lattice covers views as well as tools.

### 2026-08-03 — The escape hatch is a capability inside the lock, not a bypass
Context: Two logged open items. Deployment-time locking and the hatch were unreconciled — either the hatch is a capability granted or withheld per deployment, or it sits outside the lock. And the hatch conflicts with the prior art's central property, that the tool surface itself is the safety boundary.
Chosen: `git.raw` is a declared tool in the contract requiring its own capability and scope. It is withholdable at deploy, per declaration and per session, and wherever withheld it is **not registered** — preserving registration-as-boundary for every session that lacks it. It refuses to run if its audit line cannot be written, since attributability is the only property the definition of done claims for it. It runs a fixed executable with an argument vector, no shell, pinned working directory, system and global git configuration disabled, and a neutral home.
Rejected: **The hatch sits outside the lattice** — the literal reading of "full git is reachable", and it gives the deployment lock an exception large enough to contain every operation the safety gate blocks. **A hard floor no surface can cross** — the most falsifiable guarantee, already considered and declined in the brief; recorded as known and retained, not re-litigated. **Restrict the hatch to the console** — also already declined in the brief; the operator can now reach that posture by configuration without the design mandating it.
Reversibility: cheap to tighten (withhold it), expensive to loosen once sessions hold grants naming it.
Known and retained: an argv-level git hatch remains reachable to command execution through git's own extension points. The design says so plainly rather than implying the constraints are sufficient.

### 2026-08-03 — Clones are an evictable cache with a safety interlock
Context: The brief left the storage policy to `/design` — evictable cache, retained until the operator intervenes, or a per-declaration cap — with repository count unbounded and the standing refusal that no clone holding uncommitted or unpushed work may be discarded.
Chosen: Evictable, LRU by last operation, gated by a safe-to-evict predicate recomputed at eviction time: clean tree and index, no branch ahead of its upstream, no commits unreachable from `origin/<base>`, no stash, no open journal entry, and not `pinned`. When nothing is safe to evict, the operation that needed the space is refused and names what is blocking it. The service never deletes to make room.
Rejected: **Retained until the operator intervenes** — never surprises anyone, and it turns unbounded repository count into a disk outage that arrives as a write error mid-operation. **A per-declaration size cap** — bounds total size predictably, and evicts by an arbitrary rule rather than by what is safe to lose.
Reversibility: cheap — the predicate and the trigger are separable, and pinning everything reproduces the retained policy.

### 2026-08-03 — Restart recovery is an intent journal, not state inference
Context: Definition-of-done item 14 requires that a restart mid-operation *recovers* rather than merely detecting that something was interrupted. The brief notes that this needs intent recorded before an operation acts, which nothing in the prior art does.
Chosen: A durable journal entry written under the mutation lock, before the first side effect, carrying pre-state and per-step progress. At boot, every entry not settled is re-classified against actual repository state as not-started, completed, or partial; partial either runs the operation's declared resume step or parks the declaration in `needs-attention` with mutations blocked. Failing to write the intent record aborts the operation.
Rejected: **Infer state at boot from the repository alone** — no new persistence, and it cannot distinguish "never started" from "half applied" for any operation whose first step is idempotent, which is most of them. **Detect and report only** — the prior art's behaviour, and explicitly what item 14 rules out.
Reversibility: expensive — every mutating operation acquires an obligation to declare pre-state capture and resume behaviour.
Note: recovery never discards work to reach a clean state. "Recovers" means deterministically classified and either resumed or safely parked.

### 2026-08-03 — stdio sessions own no storage; the instance lock is an advisory OS lock
Context: The brief requires an always-on container plus a short-lived process per stdio MCP session, "two lifecycles that must stay consistent with each other", and separately requires that two instances against one storage volume are prevented rather than discouraged, including after an unclean kill left a stale lock.
Chosen: The instance lock is an exclusive advisory OS lock held open on a lease file at the volume root for the process's lifetime; the kernel releases it on death including `SIGKILL`, so there is no stale lock to reason about. The lease contents are diagnostic — they name the holder in the refusal message. A stdio process is a thin transport proxying to the always-on instance over HTTP; it never opens the volume, never takes a lock and holds no clone.
Rejected: **A lease-timestamp file with a staleness threshold and no OS lock** — works across hosts, and it has to guess how long is too long, which is wrong in both directions. **Each stdio process opens the volume** — matches the prior art, and it is the second-instance case wearing a different hat: either it defeats the lock or the lock defeats it. **stdio gets its own volume** — no contention, and two divergent sets of clones and grants for the same repositories.
Reversibility: cheap for the lock, moderate for the stdio proxy.
Note: the advisory lock protects one host. A volume bind-mounted from two hosts is unprotected, which is the "no distributed or multi-node concurrency" non-goal restated where it bites.

### 2026-08-03 — Two lock classes with a fixed order; a bounded queue, not reject-on-contention
Context: Two live options were retained for `/design`: rejecting the second caller rather than queueing, and the earlier decision that mutations serialise globally while reads and waits do not. Definition-of-done item 5 additionally requires that a running instance clones a newly declared repository *while continuing to serve every other repository*, which a global lock held for a 300-second clone cannot do.
Chosen: A global mutation mutex covering working-tree, index, `HEAD`, ref, fetch and pull-request mutations, plus a per-declaration materialisation mutex covering the initial clone and eviction. Acquisition order is always materialisation before mutation, never the reverse, which is the whole deadlock argument. Contention on the mutation lock queues FIFO with a bounded wait and a bounded depth; exceeding either returns `conflict` naming the holding operation.
Rejected: **Reject the second caller immediately** — better for agents, which handle an explicit error more gracefully than a long block, and pure friction for the console's short bursts of quick mutations. The bounded queue is both. **One lock for everything including clones** — simplest failure model, and it makes item 5 unreachable. **Per-repository mutation locks** — the natural fit for one-instance-many-repositories, and it reverses the global-serialisation decision and makes the failure model several half-done operations rather than one.
Reversibility: cheap for the queue bounds, expensive for the lock classes.
Note: a lock-free read can observe a repository mid-mutation. Read results carry the last settled `operationId` and a `mutationInFlight` flag rather than being made atomic, because taking the lock to read reintroduces the blocking the exemption exists to avoid.

### 2026-08-03 — Declaration management is operator-only, behind a remote-host allowlist
Context: The brief names `repo_declare` as an example generic tool while a binding non-goal states that a caller can never hand the service a token or a repository URL at call time. A caller able to declare a repository could attach an existing credential reference to a remote it controls and harvest the token from the first push.
Chosen: Declaration management requires `declaration.manage`, which the deployment default withholds from every MCP session profile; it is reachable from the operator console and API. Independently, a declaration's clone URL host must be on a deployment-level remote-host allowlist, and each credential reference carries its own allowed-host constraint. Two independent guards, so the property does not rest on the capability alone.
Rejected: **Declaration tools exposed over MCP** — the symmetric reading of "one canonical domain service per operation", and it opens exactly the credential-redirection route the non-goal exists to close. **Declarations held only in deployment configuration** — closes it absolutely, and makes definition-of-done item 5 (onboard by declaration alone, no restart) unreachable.
Reversibility: cheap for the capability default, moderate for the allowlist.

### 2026-08-03 — Credential isolation is scoped lookup, not an enforced boundary
Context: Deferred by an earlier decision. One process holding every credential can deliver "not given to", not "cannot be reached", and the brief's wording was softened accordingly rather than left asserting something undelivered.
Chosen: A declaration names a credential *reference*, never a value. A broker resolves the reference at the moment of use, checks it against the target host, and hands the value only into a child process's environment by name, so it never appears in a process listing and never reaches a handler. The claim stays "not given to an operation outside its declaration".
Rejected: **A process or user boundary per declaration** — the only thing that makes "cannot be reached" true; rejected because it multiplies memory across an unbounded repository count and breaks the in-process global mutation mutex, which would then need a cross-process lock the non-goals exclude. **An external secret store fetched per operation** — strongest and keeps secrets out of the container entirely; retained as a live option and now narrowed to a resolver choice (see `10-design.md` open question 1). **One shared credential** — already rejected when per-declaration credentials were chosen.
Reversibility: moderate — the reference-and-resolver shape is what a later enforced boundary would slot into.

### 2026-08-03 — Structured state in SQLite; the audit log stays a separate append-only file
Context: The design needs atomic multi-row updates for journal classification, durable OAuth grants across restarts (definition-of-done item 12), declarations, clone metadata, scheduled jobs and a notification outbox. `MCP-NEXT.md` §12.2 already prefers SQLite for durable token storage unless a spike shows its container cost disproportionate. This is a new dependency and needs the alternatives named.
Chosen: SQLite on the named volume for structured state, with explicit forward-only migrations and a timestamped backup taken before each migration runs. The audit log stays JSONL on the volume, separate.
Rejected: **JSON files for everything** — no new dependency and matches the prior art's `schedule.json`; rejected because recovery classification and grant rotation need atomic multi-row updates that a write-temp-then-rename file cannot give. **SQLite for the audit log too** — one store to back up, and it makes the audit trail share a failure mode with the thing it audits. **An external database** — a deployment prerequisite the brief never asked for, against a single-operator container app.
Reversibility: expensive — the schema and the migration policy propagate into backup, restore and rollback procedure.
Note: forward-only migrations plus definition-of-done item 18's tested rollback are only compatible because of the pre-migration backup. Without it, rolling back the image cannot roll back the store.

### 2026-08-03 — One result envelope, widened to eight kinds, with a rule that generates `isError`
Context: The prior art's envelope has four kinds (`success`, `validation`, `precondition`, `infrastructure`) and sets `isError` only for `infrastructure`, because a gate correctly reporting three bad tags executed perfectly. `MCP-NEXT.md` §9.3 defines seven categories including `authorization`, `conflict`, `upstream` and `timeout`. Two vocabularies cannot both be the contract.
Chosen: One envelope, eight kinds, `isError` derived from a single rule — true when the failure is about the service or its dependencies (`upstream`, `timeout`, `infrastructure`), false when it is about the request or the repository state (`validation`, `precondition`, `conflict`, `authorization`). Token, audience and issuer failures never enter the envelope; they are transport-level `401` with a resource-metadata challenge, because the caller has to be told where to authenticate. Scope and capability failures at dispatch do produce an `authorization` envelope, and are audited.
Rejected: **Keep the prior art's four and map the rest onto them** — no migration for existing consumers, and it collapses distinctions the runtime pipeline needs to make. **Adopt §9.3's seven verbatim** — no reconciliation work, and it drops `success` and the `validation`-as-normal-result semantics that make the gate tools honest. **Per-kind `isError` decided case by case** — flexible, and it guarantees drift, because nobody can restate the rule from the table.
Reversibility: expensive — it is the client-visible shape of every result on every surface.

### 2026-08-03 — The scheduler holds one registry-named operation, not a publish
Context: The brief calls for the scheduler to be generalised into a hold-and-act mechanism taking the operation as a parameter, and calls it a redesign rather than a move. "The operation as a parameter" sits close to both the workflow-engine non-goal and the no-runtime-module-resolution rule.
Chosen: A job names one tool from the compiled registry, annotated schedulable, with input validated against that tool's schema at creation. It dispatches through the same pipeline as any caller under a scheduler actor profile. The creator's effective capability set is frozen on the job and re-intersected with the current grant at fire time, so a job can lose capability but never gain it. The prior art's explicit per-job missed-tick policy is inherited whole.
Rejected: **An ordered sequence of tools** — enough for stage/commit/push/PR/wait without becoming a language, and it is the flows layer the brief defers. **Keep a publish-shaped tool and parameterise it** — smallest change, and it carries the blog's shape into the generic surface, which is the coupling this extraction exists to remove. **Re-derive capability at fire time only** — simpler, and it lets a job created under a narrow grant execute under a later wider one.
Reversibility: cheap.

### 2026-08-03 — Console extension via a versioned package consumed at the derived build
Context: Logged as deferred to `/design`. Extension happens at image build, but the console is a separate frontend project and a bundle must be built to gain routes.
Chosen: The base publishes its console as a versioned package — sources, view-registration types, build entry. The derived image's build consumes it and produces the bundle. The bundle's asset manifest is hashed into a console fingerprint, separate from the contract fingerprint; both are verified at startup and reported by the version endpoint, and a mismatch is fatal. A registered view declares the capabilities it needs and renders for a selected repository only when that repository's grant contains them.
Rejected: **A prebuilt bundle that discovers views at runtime** — no consumer build step, and it puts the UI outside anything fingerprinted, defeating the reason image-build extension was chosen. **The derived image rebuilds from base sources copied out of the base image** — no extra publishing step, and no version pinning and no type checking across the seam. **The consumer forks the base console** — nothing to maintain across the seam, and every base improvement becomes a merge.
Reversibility: expensive — an extension seam is hard to retrofit, and this one is also a published package boundary.

### 2026-08-03 — `gh` kept, behind a host-adapter interface
Context: Retained as a live option by an earlier decision, which noted the unbounded-targets decision would force the question. Roughly a third of the generic tool set is GitHub-shaped.
Chosen: One host-adapter interface with a single implementation, GitHub via `gh`, isolated in one module. A declaration states its host; `generic` gets local git only and no `host.*` capabilities. A per-credential request budget with jittered backoff sits in front of the adapter, because unbounded repositories multiplied by polling monitors reaches the host's rate limits before disk becomes binding.
Rejected: **Call GitHub's REST and GraphQL APIs directly** — one less binary in the image and honest for a GitHub-only feature set; rejected because parity against captured fixtures is a definition-of-done item and swapping the host client during that migration adds risk with no stated benefit. The interface keeps the swap additive. **A host abstraction proven against a second implementation** — the only thing that makes "no assumptions about host" fully true, and materially the largest option with no second host in evidence.
Reversibility: cheap — the interface is the seam, and the prior art already isolates `gh` in one module.

### 2026-08-03 — Federation is OIDC with a subject allowlist; TOTP recovery is codes plus volume break-glass
Context: The brief requires one operator identity provable two ways, federation over "one standard protocol with a configurable issuer", and enforced TOTP with a working lockout-recovery path and no second operator to let you back in. A logged open item noted that an external provider will happily assert many identities and something must reduce that to one authorised subject.
Chosen: OIDC as the protocol, matching `MCP-NEXT.md` §5.4's preferred external-authorization-server mode. The deployment configures an issuer and an allowlist of acceptable subject claims, all of which map to the single operator identity — many credentials, one identity. Recovery is single-use codes generated at enrolment and stored hashed with the remaining count reported, plus an out-of-band break-glass: a one-time reset token placed in the storage volume by whoever has host access, consumed at next login and audited.
Rejected: **SAML** — broader enterprise reach, and a second protocol family alongside the OAuth the service already speaks in both directions. **Accept any subject the configured issuer asserts** — simplest, and it makes the identity provider's user list the service's; a single-operator system with an implicit multi-user door. **Recovery codes alone** — no host-access dependency, and it fails exactly the case item 10 names: codes lost along with the authenticator.
Reversibility: cheap for the allowlist, expensive for the protocol.
Note: break-glass reduces recovery to volume access, which is the operator's real root of trust. That is stated rather than hidden — anyone who can write to the volume can already replace the image.

### 2026-08-03 — Outbound notification is a webhook-first outbox on terminal states
Context: The brief reopened outbound notifications as in scope with the mechanism undecided, on the grounds that an unwatched run stopping at a terminal state must be able to reach the operator, otherwise "unwatched" means "unnoticed".
Chosen: A notifier module behind one port with a single shipped transport — an HTTP webhook POST to an operator-configured URL — fired on terminal states an unwatched caller cannot see: merge conflict, failed required check, wait timeout, recovery parked in `needs-attention`, and eviction refused for disk pressure. Delivery goes through a durable outbox with bounded retry, never blocks the operation it describes, and logs on exhaustion.
Rejected: **Email first** — reaches the operator without another service, and it needs SMTP configuration and carries deliverability failure modes that are themselves silent. **An MCP server-initiated notification to the connected client** — no extra transport, and no client is guaranteed connected, which is the definition of unwatched. **No notifier, rely on the console** — smallest, and it makes item 13's standing property depend on the operator looking.
Reversibility: cheap — one port, one adapter.

### 2026-08-03 — `.gitattributes` pins LF; `core.autocrlf` overridden per repository
Context: Every commit warned "LF will be replaced by CRLF the next time Git touches it". `core.autocrlf` is `true` on the primary Windows host, so checkouts would carry CRLF while the house convention in `AGENTS.md` is LF. This project ships a container with an entrypoint script, and a shell script checked out with CRLF fails inside a Linux container with a bad-interpreter error naming neither the script nor the line endings.
Chosen: `* text=auto eol=lf` in `.gitattributes`, plus explicit `binary` for raster and archive types. One file, effective on every host and every clone regardless of local git configuration.
Rejected: **Force LF for scripts only** — narrower, and it leaves two rules to remember whenever a new file type appears. **Defer until the first script exists** — which is exactly when someone is already debugging a container that will not start. **Set `core.autocrlf=input` globally on the host** — fixes every repository at once and silently changes behaviour for the other twelve in the estate.
Reversibility: cheap, though a later change would rewrite the working tree of every clone.

### 2026-08-03 — Tool renaming is a clean break at cutover, no aliases

### 2026-08-03 — The mutex covers mutations only, not reads or waits
Context: The brief said "one operation at a time, globally across all repositories". `blog-mcp` serialises repo-mutating calls only — `blog_diff` and every read tier run outside the mutex — and every `wait_*` tool caps at 1800 seconds. Under the literal reading a single CI wait would hold every repository for up to half an hour.
Chosen: Repo-mutating operations serialise globally. Reads and monitoring waits run outside the lock.

### 2026-08-03 — Credentials are per-declaration and isolated
Context: A consequence of one-instance-many-repos that no interview answer had reached. `blog-mcp` needed exactly one credential and took it from the environment; per-repo containers gave credential isolation for free. A single instance removes that property silently.

### 2026-08-03 — One instance serves many repositories; `blog-mcp`'s one-repo-per-container model dropped
Context: `blog-mcp` binds one container to one repository — a single `BLOG_MCP_CLONE_URL`, a single `/workspace/repo`. Reversibility: expensive — credential scoping, storage layout, the declaration format and the console's information architecture all follow from it.

### 2026-08-03 — Globally serialised by an in-process lock; "no locking" retracted
Context: An earlier interview answer made "no queue, no locking, no contention handling" a binding non-goal. Reading `blog-mcp/src/exec/repoLock.ts` contradicted it: that lock exists because the UI, external MCP clients and the scheduler share one working tree and one HEAD, and without it concurrent branch switches corrupt HEAD and `git add` hits `index.lock`. This project has the same three surfaces, and now serves many repositories from one process.
Chosen: One operation at a time, globally across all repositories, enforced by an in-process lock. `blog-mcp`'s promise-chain queue is the precedent. The non-goal narrows to distributed and multi-node concurrency.
Rejected: **Genuinely no lock** — the reference's own comments record that this corrupts HEAD in practice. **Reject the second caller rather than queue** — arguably better for agent callers, which handle an explicit error better than a long blocking wait; retained as a live option for `/design`. **Per-repo locks with parallel operation across repositories** — the natural fit for one-instance-many-repos and the most capable; rejected to keep the failure model at exactly one half-done operation.
Reversibility: cheap to tighten, expensive to loosen — the serial assumption will spread through the workflow layer.
Note: The retracted non-goal was a category error worth naming. One-operation-at-a-time is the *outcome a lock produces*, not the absence of one.
